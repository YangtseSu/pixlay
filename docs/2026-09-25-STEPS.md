### The research of 2026-09-25 (finding 3), recorded

**The human ruled the same day (ruling 36, amended): the platform's own save dialog is the answer** —
no in-dialog browser and no folder-only chooser. What follows is the record of why one was asked for and
what building it would have cost; it stays as the evidence behind that ruling.

- **GTK has no embeddable file chooser any more.** `GtkFileChooserWidget`, the only widget that could be
  put inside our own dialog, is **deprecated since GTK 4.10** (`Gtk-4.0.gir`: `deprecated="1"
  deprecated-version="4.10"`, "Direct use of `GtkFileChooserWidget` is deprecated"; the whole interface
  lives in `gtk/deprecated/gtkfilechooser.c`), and `gtk4-rs` marks its constructors
  `#[cfg_attr(feature = "v4_10", deprecated …)]`. This workspace builds with the `v4_12` feature and
  `clippy --workspace --all-targets -- -D warnings`, so using it fails the verification entry unless it is
  wrapped in `#[allow(deprecated)]` — a legacy path, which `AGENTS.md` forbids.
- **The folder is chosen by `GtkFileDialog::select_folder`** if we keep the platform's chooser: still a
  second dialog, but a *folder* dialog (no name, no extension), which is one question rather than two.
- **Or the folder browser is built**: `GtkDirectoryList` (a `GLib` model over a directory, not deprecated)
  + `GtkListView` + a hand-built path bar (`GtkPathBar` does not exist in GTK4), with its own keyboard,
  accessible names and tests — a component of its own, and the app's only directory browser. That is the
  part the human said to ask about before building.
- **"Remembered" has a second question**: the last export's folder lives in the window today
  (`export::Settings`), so it dies with the session. Remembering it across runs needs a file under
  `~/.config/pixlay/` — and ruling 8 of 2026-09-22 says "No configuration file".

## S18 · The switch has a number

**Goal**: turn the human's finding 1 ("switching a layout takes too long") into a measurement and a budget,
before any code changes — the shape S12 used for the preview's cost.

- **Work**: a CLI ruler, `pixlay-render switch --project <p> --template <t> --px <n> [--stats]`, doing
  exactly what the window does on a layout change — apply `SetTemplate`, derive the new grid, build the
  preview-grade sources, render — and reporting `ms` **split into the phases** (template/geometry,
  sources, composite) plus `peak_rss_mb`; a GUI-side test that drives the window's own path (the click to
  the frame that shows the new render) and prints the same numbers; the band's share measured by the same
  run with and without the gallery rebuild.
- **Exit criteria**: the subcommand exists, is deterministic, locale-free and documented in `--help`;
  the window's number and the CLI's agree within their own noise, both recorded in this step's Result; the
  budget is a named constant with its measured source inline (`AGENTS.md`, "Measurement rules"); peak
  memory is `VmHWM`, time is `CLOCK_MONOTONIC` split by phase.
- **Not doing**: no optimisation in this step — the number decides, and the ruling (the gate above) either
  closes the step or adds the step that optimises.
- **Human**: the number rules at this step's Result (see the gate table).

### S18 · Result (2026-09-25)

**The work is done and its criteria are green, and the step is ⏸ because the gate's ruling is what is
missing** (`AGENTS.md`: a step becomes ✅ only when its gate ruling is on disk). This subsection is the
record that ruling is written against; nothing is pending on the code side, and nothing was optimised —
the number decides.

- **The two rulers measure the same click and agree.** `pixlay-render switch --project <p> --template <t>
  [--canvas <w>x<h>] [--band] [--stats]` drives the window's own path in a windowless process, and
  `crates/pixlay/tests/switch.rs` drives the band's own cells in the window and times the click to the
  frame that shows the new render. Same rows, same grid, three consecutive runs each on a quiet machine:
  `mosaic-8-s14 → strip-8-8x1` **CLI 123.5 / 124.6 / 124.8 ms** against the **window 149.0 / 151.0 /
  151.1 ms**; `→ grid-8-4x2` **176.9 / 176.9 / 179.0** against **204.1 / 206.7 / 204.0**. The window is
  the CLI **+26 / +27 ms** — one 16.6 ms display frame plus the blit and the paint, which a windowless
  command cannot reach — and that single offset is the whole of the difference, which is what "agree
  within their own noise" means here.
- **The budget is a named constant with its measured source inline**: `SWITCH_BUDGET_MS = 210.0`
  (`crates/pixlay-cli/src/cli.rs`), the worse row's worst run rounded up to the next 10 ms. It governs the
  **canvas half** (`switch_ms`), because the finding is about the picture on the canvas; the band's rebuild
  is `band_ms` beside it.
- **The three phases are the plan's**: `template_ms` 0.013–0.014 ms (the `SetTemplate` and the grid
  derivation), `sources_ms` 80.1–100.2 ms (the preview-grade copies), `composite_ms` 42.2–79.2 ms (the cell
  bitmaps) — measured by `CLOCK_MONOTONIC` (`crate::stats`), with `peak_rss_mb` from `VmHWM` (63.8–65.6 MB
  for the CLI's whole process).

  sheets with dark lines at their own aspects, the chosen one inside the accent border, every layout
  readable at 128x96.

**Decisions this step made** — each one a place where the plan's own sketch met the geometry:

1. **The per-candidate grid stays, and what is fixed is the box.** The Work text said
   `candidate_templates()`'s per-candidate grid "becomes one fixed thumbnail grid". One *fixed grid* cannot
   be right: a sketch is the sheet, and the sheet's shape is the template's aspect, so drawing every
   candidate into one 128x96 grid would either stretch the geometry or pad it with paper that reads as a
   margin — and ruling 32's "a sketch is a complete account of it" forbids both. `CANDIDATE_BOX` is fixed,
   and `candidate_grid(aspect)` derives the sheet's own grid from it exactly as it did for a render.
2. **The sheet's own edge is stroked too.** A cell that reaches the sheet's border loses the outer half of
   its line to the surface, so without this the sheet's right and bottom edges would have no line at all
   while the top and left had one. The edge is stroked inset by half a stroke, so the ink is inside the
   paper on all four sides; a template whose cells keep a margin shows both rectangles, which is its
   geometry.
3. **Half a pixel of translation, so lines land on pixel centres.** A one-pixel line centred on a pixel
   *boundary* covers two pixels at half each — a grey, two-pixel line (measured: a two-cell strip's seam at
   x = 64.0 was 127,127,127 on columns 63 and 64; at 64.5 it is 0,0,0 on one). The shift is in the sketch
   only; `draw` is untouched.
4. **The band's build stays on the worker; its decode counter went.** A sketch is 0.15 ms, so the thread hop
   is not for the cost — it is for where the strip may be mutated (a rebuild delivered on the main context,
   never inside the layout signal that asks for it) and for the S18 ruler's shape. `GalleryReply.decodes`,
   `Window::gallery_decodes` and their accumulation are deleted: the job cannot name a file, so the counter
   could only ever be 0, and `tests/layout.rs` asserts the claim on `decoded_sources` instead. The S18 ruler
   still measures the band's rebuild (`--band`, `gallery_builds`), which is what its budget reads.
5. **The two colours come from the theme, through CSS and `Widget::color()`.** A sketch draws *pixels*, so
   it cannot use a style class directly; `style.css` gives `.sketch-paper` / `.sketch-ink` the theme's
   `@view_fg_color` / `@view_bg_color` and two invisible probe labels in the band resolve them (measured:
   paper 255,255,255 · ink 29,29,32 in the dark style). The style context's `lookup_color` is deprecated
   since GTK 4.10, so this is the only non-deprecated way to read a theme colour back — and no colour is
   named in Rust.
6. **`render --template <name> --sketch` is the CLI's spelling** (the plan offered this and
   `templates --sketch`). A sketch is one template's geometry, which is the band's own unit: one call, one
   image, one grid — where `templates --sketch` would have had to invent a file-naming scheme for N
   candidates and a contact-sheet layout nobody asked for. `--paper` / `--ink` / `--stroke` come with it and
   default to the renderer's own white / black / 1 px; `--project`, `--preview-px` and the frame flags are
   refused with it, because a sketch has no document to apply them to.
7. **`switch --band` draws with the renderer's default colours.** It measures *time*, and the two colours do
   not change the work; the window's own band passes the theme's.

## S23b · What the canvas takes from outside

**Goal**: ruling 41 — a drop lands where it is aimed, the clipboard works on a cell's photo, and everything
that arrives is one undo step. The drag *from* the file manager exists (`crates/pixlay/src/canvas.rs`'s
`DropTarget` hands the paths to `window.drop_files`), and a paste is the new half.

- **Work**:
  - **the drop's rule changes.** Today a drop fills *empty* cells from the drop point onward and only
    replaces when there is no empty cell left, so one file dropped on an occupied cell can land in a
    different cell entirely — the pointer's promise and the result disagree. The new rule: the first file
    takes the **cell under the pointer** (filling it, or replacing what it holds), the rest fill the empty
    cells from there on in reading order (wrapping), and files with no cell left are **ignored with one
    report** (ruling 34's shape). A drop never replaces a cell it did not land on.
  - **one drop, one command.** `window.drop_files` currently calls `place_photo` per file, which is
    `Command::SetSource` per file — a five-file drop is five undo steps. It becomes one command
    (`Command::PlacePhotos { places: Vec<(usize, PathBuf)> }`), validated like every other command.
  - **the clipboard**: `Ctrl+C` / `Ctrl+X` / `Ctrl+V` (menu items in the main menu's own Edit group, with
    the sensitivities: copy/cut need a selected cell that holds a photo, paste needs a selected cell and a
    clipboard holding a photo we can use). `Ctrl+C` puts the photo's path on the clipboard as
    `text/uri-list` — so it can be pasted into another application, and so a paste from another
    application arrives in the same shape — and a cut additionally remembers its source slot; paste into
    the selected cell is `Command::SetSource` (the target keeps its own framing, which `draw` re-fits —
    the same rule as Replace), and a paste that follows a cut is **one** command
    (`Command::MovePhoto { from, to }`) that empties the source; the cut state is dropped if a command
    changes the cell count, because the source slot no longer means the same cell.
  - **what another application's clipboard can hold**: `text/uri-list` (the file manager) behaves exactly
    like a drop of those files at the selected cell; a **bitmap** with no file behind it is written out as
    a PNG first — a document references *paths*, and a cell whose source is not a real file is a cell that
    cannot be reopened. The step decides where it is written (the cache under `$XDG_CACHE_HOME` is the
    default; the project's own directory when the document has one is the alternative) and records the
    answer in `docs/CONTRACT.md`, with the exit criterion below forcing it to be sound.
  - whatever the accelerators table gains (`win.copy` / `win.cut` / `win.paste`), the shortcuts dialog, the
    menu, `po/`, `docs/HIG-REVIEW.md`'s keyboard and writing-style rows and `docs/CONTRACT.md` §5 (the new
    command, and the drop's rule) follow in the same commit.
- **Exit criteria**: a three-file drop on cell 4 of the eight-photo verification document lands them in
  cells 4 and 5 plus the next empty cell, replaces cell 4's photo, and is **one** undo step (asserted from
  the history); a drop of twelve files lands nine and reports once; a drop on an empty cell fills it and
  touches nothing else; `Ctrl+C` + `Ctrl+V` moves a photo between two cells in both the replace and the
  fill case; `Ctrl+X` + `Ctrl+V` is one undo step and leaves the source cell empty; a bitmap placed on the
  clipboard by the test pastes into a cell whose source is a file that survives a save and a reopen; the
  paste items are insensitive with no cell selected and with a clipboard holding nothing usable; the CLI
  can produce the same document (`edit --slot i --photo p` per cell, `--clear`, `--swap`), and `cargo
  test`'s CLI suite is untouched.
- **Not doing**: no drag *out* of the app (a photo leaving for the file manager), no clipboard for the
  whole document or for a whole collage, no camera or portal integration, no multi-select of cells to copy
  several photos at once.
- **Human**: whether the drop and the paste rules read as expected (at the walk gate).
