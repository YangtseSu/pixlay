**This plan began on 2026-09-22** (the commit that added this file), and that is the date in its name.
It replaces the plan of 2026-09-20, which is retired — its text, S7's implementation and its void human
walk are in [`docs/archive/2026-09-20-STEPS.md`](archive/2026-09-20-STEPS.md). The review that produced

the evidence against forking Loupe, and the rulings below in their original wording.

**The S-numbering continues** from the retired plan (which ended at S8) so that the S1…S7 citations
already written into code comments keep resolving: S9 is the first step here.

Run the steps in order. **One step at a time**; finish a step before starting the next.

The first sentence for a new session:

> Read `AGENTS.md`, then read `docs/2026-09-22-STEPS.md`. Do only the step the "Current progress" line under "Status" points at, and do not start later steps ahead of time.
> After finishing a step, run that step's verification command, turn its exit criteria into tests, write the outcome into that step's "Result" subsection, then update its status row and the "Current progress" line.

- Hard constraints and invariants are in `AGENTS.md`; this file only orders the steps and gives the exit
  criteria, and does not repeat their content. The measurement rules, and how a constant's source is
  annotated, are in `AGENTS.md` too ("Verification entry").
- How the steps are split, and the three cases in which a step must end a session, is `AGENTS.md`'s
  "Step discipline".
- Before starting a step, run `cargo test` once to confirm the baseline is green.

## Ruling (2026-09-22, human): the purity cut

Asked to make the product **only** a photo collage, the human ruled four things out of it. Each one is a
removal, not a change of behaviour, and together they take S12c.

| # | Question | Ruling |
|---|---|---|
| 13 | Canvas-level text layers (S5), the tiled watermark included | **Removed.** No text of any kind: no layer, no watermark, no `{date}` / `{filename}` / `{index}` token, no `textFallback`. |
| 14 | Per-slot grading and the one-click canvas-wide filter (S4) | **Removed.** A collage places photos; it does not colour them. |
| 15 | The ten-slot recipe (`strip-10-10x1`) and `MAX_SLOTS` | **Removed.** Ruling 3's cap is 9, so a ten-slot layout was already unreachable from every surface; it stops being expressible at all. |
| 16 | Output formats and the export form | **PNG and JPEG only** — TIFF goes, and with it the JPEG `--chroma` flag. The window's export form keeps **one quality option** (the export resolution); the sheet size stays a document field, reached from the CLI. |

The basis, in the order the cuts pay for themselves:

1. **None of it is on the main path.** Ruling 12's path is `open → pick 2–9 photos → pick a layout → adjust →
   export`, and the human's own stage list has no text (`docs/2026-09-22-UX-DIRECTION.md` §9 puts "poster mode
   (presets + text styles)" out of scope). Grading is an editor's control in a product whose per-cell
   capabilities ruling 11 fixed as *zoom, move, rotate*.
2. **Text is the one feature whose pixels depend on the host.** `pixlay-render` asks fontconfig for the generic
   `sans-serif` (`crates/pixlay-render/src/text.rs`), so the same document renders differently on two machines —
   against `AGENTS.md`'s "identical input yields identical output". The measurements only looked reproducible
   because the tests pin a font through `FONTCONFIG_FILE`.
3. **Each cut removes a dependency or a whole pipeline stage.** Text takes `pangocairo` (and the `pango` chain)
   out of `pixlay-render`; TIFF takes `tiff`/`weezl` out of `pixlay-imaging`; grading takes one of the two
   colour stages out of the frozen evaluation order.
4. **A document field is cheapest to remove now.** `CollageDoc` is read with `deny_unknown_fields`, so deleting
   `text` / `filter` / `textFallback` / `grade` refuses every project a previous build wrote. That is why
   `DOC_VERSION` moves to 2 for this cut, and why it happens *before* S16 packaging: once S16 has shipped, a
   `.pixlay` in a user's home turns the same cut into a migration decision.

## Ruling (2026-09-22, human): pixels, not paper

Asked where an export's size comes from — a physical canvas times a resolution, or a pixel count — the
human ruled: **paper was never part of this product and the size is controlled in pixels directly.**
Pixels are the only size the product knows, and S12d executes it. This **amends ruling 16**: its clause
"the sheet size stays a document field, reached from the CLI" is exactly what is overruled —
`edit --sheet` and the field it set go with it.

| # | Question | Ruling |
|---|---|---|
| 17 | Where does an export's size come from: a physical canvas × a resolution, or pixels? | **Pixels only.** `CollageDoc` loses its `canvas` field; millimetres, DPI and every conversion between them leave the code, the flags and the files; **one pixel count (the long edge)** sizes every render, and the window's quality row is that number. |

The basis, in the order the cut pays for itself:

1. **A raster's only intrinsic size is pixels.** Millimetres × dpi is a print instruction layered on top
   of pixels — the same file prints at whatever size its reader divides it by — and this product was
   never asked to speak for a printer. Paper entered as scaffolding: S0's performance spike measured an
   A0 render, and S6 made the file carry the resolution it was asked for. Neither made paper part of what
   a document *is*, and ruling 16's `edit --sheet` (2026-09-22, this morning) kept the concept alive one
   step longer than it was ever requested.
2. **It deletes the last cross-field consistency rule.** "The canvas's aspect must equal the template's"
   existed only because two fields each described the same shape; the export grid's shape *is* the
   template's, so the mismatch becomes unrepresentable instead of validated.
3. **It collapses the export surface to one number.** The window's quality row, `render`'s size flag and
   `probe`'s grid all become the same long-edge pixel count: no conversion, no rounding rule to freeze,
   and no resolution in a file that nobody chose.

## Ruling (2026-09-22, human): no utility pane

Asked whether the sidebar still earns its place once every group it holds has a home elsewhere, the
human ruled it does not: the pane goes, and an `Export…` dialog carries the three export questions —
the format, the output quality, and the filename with a path chooser, asked when Export is pressed.

| # | Question | Ruling |
|---|---|---|
| 18 | The utility pane (`AdwOverlaySplitView` + `AdwPreferencesPage`, the Template / Photo / Framing / Export groups) | **Removed, in the UI steps that own its groups.** Each group already has a home: the template combo becomes S14's candidate gallery, the photo buttons are S13's picker plus S14's add/remove and S15's replace/clear, framing is S15's floating buttons plus the gestures, and export becomes the `Export…` dialog below. What has no other home — the frame's gap/radius/colour — moves into a small `Frame…` dialog of the same shape rather than keeping the pane alive for three rows. |

The basis:

1. **A linear three-minute flow has no use for a permanent panel.** The pane was the editor's
   instrument board; the product is now `pick → layout → compose`, and each stage owns its own
   controls (the tray, the gallery, the floating buttons, the dialog). Keeping the pane would mean
   maintaining two surfaces for every one of those decisions.
2. **The export dialog is the standard shape, not an invention.** GTK4's `GtkFileDialog` takes no
   custom widgets, so format + quality + filename-with-path-chooser as rows of an `AdwDialog` is
   the platform's own answer — the same shape the unsaved-changes confirmation already uses.
3. **The frame dialog is the same shape for the same reason.** Three normalized rows behind a
   header-bar `Frame…` button on the compose stage, like `Export…`: one pattern for both
   document-level questions, neither of them a permanent row.

## Ruling (2026-09-22, human): the picker, as gthumb has it

Shown gthumb and loupe at work — both cloned under `~/projects` (`gthumb` at 4.0.rc, `loupe` at 51.0.0,
both read on 2026-09-22) — and asked why the picker does not look like them, the human ruled that the
copy of gthumb's interface is not good enough: the media area takes the vast majority of the page, the
thumbnails fill the full width, the picked list is as tall as the media area, a status bar closes the
window, and clicking a row of the right-hand list switches the preview to that photo. The preview image
being drawn too large is a real defect, not a matter of taste. On the theme, the ruling is that HIG
states the dark theme is the default for video and audio applications. The look that is being copied
is in two screenshots of the reference (3839x2159 device px on a 2× display); every number in this
ruling is measured off them.

| # | Question | Ruling |
|---|---|---|
| 19 | The picker's proportions and arrangement | **The media area takes the vast majority of the page; the thumbnails are one row along its bottom, spanning the full width; the picked list runs down the right edge at the media area's own height; a status bar closes the window.** S13b's arrangement — a small preview above a tall grid, with the picked list down the full page — is superseded. |
| 20 | The bottom of the window | **A status bar with four fields, in gthumb's order: `picked / total`, the photo's pixels, its file size, and the current zoom percentage.** |
| 21 | The picked list | **Clicking a row switches the preview to that photo.** S13b's list only selected (the preview followed the *grid's* click). |
| 22 | "The preview image is too large — you definitely copied it wrong" | **The decode is the size that is drawn, and a cell is gthumb's own size.** `preview_px` follows the photo's *fitted* device size (S13b asked for the pane's long edge whatever the photo's aspect), and **`TILE_SIZE` goes 256 → 128 logical px**: gthumb's `thumbnail-size` default of 256 is *device* pixels, and the reference's own cells measure 250 device = **125 logical** on this 2× display, so S13's ruling read the unit wrong and our cells are twice as big as the app they were copied from. |
| 23 | The theme | **The app is dark by default.** HIG `guidelines/ui-styling`: "apps can alternatively choose to use the dark style by default … **primarily recommended for apps which display rich visual content like images or video**", and both reference apps do exactly that — gthumb `style_manager.color_scheme = Adw.ColorScheme.FORCE_DARK` (`gthumb/src/Application.vala:676`), loupe `// Force dark theme` + `set_color_scheme(adw::ColorScheme::PreferDark)` (`loupe/src/application.rs:76-79`). `AGENTS.md`'s "never force light or dark" is **superseded**; "no per-app style preference" **stands** (neither reference app has one, and a stored preference would need a settings file — ruling 8). |
| 24 | Buttons and menus | **They follow the two references and HIG `patterns/containers/header-bars`**: primary and navigation actions at the **start**, the heading in the **centre**, the menu at the **end**; one **primary menu** with sections, in the shape both apps use ([new / open / import] · [view options] · [keyboard shortcuts, about]). S13b's headers put *every* control at the end and styled the flow's Next button `suggested-action`, which HIG asks header bars to avoid. |

### What the reference actually measures

Both screenshots are the whole screen (3839x2159 device px, a 2× display), the app window starting under the
26-logical-pixel GNOME top bar. Measured off them (`magick`, 2026-09-22; device px, logical = device / 2):

| Band | Reference | Logical |
|---|---|---|
| header bar | y 54..128 | 38 |
| **media area** (the photo's backdrop) | y 132..1851 | **860** |
| **thumbnail row** | y 1852..2080, cells left-aligned from x 41, pitch 250 | **114**, cells **125** |
| **status bar** | y 2094..2157 | **32** |
| media area as a share of the content band (y 132..2080) | 860 / 974 | **88 %** |
| the media backdrop's colour | `#222226` | = libadwaita's dark `--window-bg-color` (measured: `@define-color window_bg_color #222226` in libadwaita 1.10's dark block) |
| the status line itself | `6/6   1254 × 1254   1.1 MB   79%` | count/total · pixels · size · zoom |

And the reference's own code for the pieces being copied:

- **The dark app**: `gthumb/src/Application.vala:676` `style_manager.color_scheme = Adw.ColorScheme.FORCE_DARK;`
  (unconditional, inside `init_settings ()`), the same function that installs the stylesheet
  (`:678-680`); `loupe/src/application.rs:76-79`. HIG `guidelines/ui-styling` is quoted in ruling 23.
- **The media backdrop**: loupe draws it as a constant colour (`src/widgets/image.rs`,
  `BACKGROUND_COLOR_DEFAULT = #222226`) and re-guesses it per image
  (`src/widgets/image/background_color.rs`); gthumb pins a class — `data/css/style.css:5-7`
  `.image-view { background-color: #111; }`, applied at `src/Ext/Image/ImageViewer.vala:17`. **We copy the
  idiom, not the literal**: dark by default and the media area on the theme's own background — which *is*
  `#222226` in the dark scheme, exactly what both references show — because HIG `guidelines/ui-styling:39`
  asks custom styling to use the theme's variables.
- **The thumbnail row**: gthumb's grid is `GtkGridView` with `max_columns=15`, class `thumbnail-grid`
  (`data/ui/file-grid.ui:14-20`), styled `data/css/style.css:26-42`: `.thumbnail-grid { padding: 10px }`,
  `> child { margin: 10px; border-radius: 10px; border: 1px solid var(--dimmed-border-color) }`,
  `.thumbnail-card { padding: 6px; border-radius: 4px }`, and the drop-target edge in the accent. The cell
  size comes from `thumbnail-size` — **default 256** (`data/schemas/org.gnome.gthumb.gschema.xml:31-33`),
  adjustable 128..512 in steps of 32 (`data/ui/browser-preferences.ui:82-89`) — and is consumed as
  `thumbnailer.requested_size` (`src/FileGrid.vala:21-27`), i.e. in the *device* pixels the thumbnailer
  produces. loupe's own thumbnail constant is also 128 (`src/widgets/image.rs: THUMBNAIL_SIZE 128.0`).
- **The zoom readout**: gthumb `zoom_info.label = "%d%%".printf ((int) Math.round (image_view.zoom * 100));`
  (`src/Ext/Image/ImageViewer.vala:665`); loupe formats `"{} %"` from
  `(zoom_target * 10_000.).round() / 100.` (`src/widgets/image_view.rs`) and shows it in the zoom popover.
  **100 % means one image pixel per device pixel in both** (loupe: `applicable_zoom = zoom_normalize(zoom)
  / scaling`).
- **The status line's fields**: the pixel pair is `"%d x %d"` (`gthumb/src/lib/util.c:921`), the size goes
  through `GLib.format_size`, the position is `"%d"` + `" / %u"` (`src/ViewerStatus.vala`), and gthumb's
  browser keeps them in a `GthStatus` inside the bottom bar's right-aligned cluster
  (`data/ui/browser.ui:382-391`, styled `.statusbar { padding: 4px }`).
- **The chrome**: HIG `patterns/containers/header-bars` (primary buttons at the start, heading in the centre,
  menus at the end; group with spacers; tooltips on primary controls; avoid text-only and suggested-action
  buttons in a header bar). gthumb's browser header bar: start = [previous, next, up, reload, selections],
  end = [presentation, properties, edit, comment, Tools, hamburger]; its hamburger is 10 items in 3 sections
  (New Window, Open…, Open Clipboard, Import Files · Sort Files, Sort Folders, Hidden Files · Preferences,
  Keyboard Shortcuts, About). loupe's: 5 sections (New Window, Open… · Open With…, Print… · **Rotate** as
  `display-hint="inline-buttons"` · Set as Background…, Delete · Help, Keyboard Shortcuts, About). Both
  load their menus from per-page `.ui` models; loupe's zoom and prev/next controls are **overlay controls on
  the photo** (bottom-left and bottom-right, faded out after 3 s idle), and its header bar is a `LpShyBin`
  so a long filename cannot grow the window.
- **The shortcuts**: gthumb keeps them as **data** in one table plus a manual key dispatcher
  (`src/Ext/Shortcuts/Shortcuts.vala:132-294`, `MainWindow.vala:1040-1067`, `:1218-1220`) and shows them in
  an `AdwShortcutsDialog`; loupe declares them per action and ships a `shortcuts-dialog.ui`. pixlay already
  does the data-table half (`crates/pixlay/src/app.rs::ACCELERATORS`), which is the same idiom and stays.

**How a status is marked.** The status row above, the marker on the step's own heading, and the "Current progress" line are three renderings of the same claim and must always agree; changing one is part of closing the step. ## S9 · Library and selection on the CLI — ✅ done (2026-09-22)

**Goal**: stages 1–2 of the flow exist as machine surface, so the picker's pixels and its cost can be
measured without a window (`AGENTS.md`: nothing may be possible only in the GUI).

- **Work**:
  - `pixlay-render scan --dir <path>`: the image files of a directory as JSON — path, mime type, size
    *after* EXIF rotation, the EXIF date when there is one, and `mtime`; ordering is lexical by path and
    stable across runs; a file the decoder refuses is a row with its reason, not a silent skip. No
    recursion unless `--recursive`.
  - `pixlay-render thumb --photo <path> --px <n> --out <file>`: one thumbnail's pixels as a file, so the
    picker's expensive half is a CLI number (`AGENTS.md`: a visual conclusion must become a number).
  - `pixlay-render init --template <name> --photo <p>… --out <file>`: extends the existing `init` with
    photos, **argument order = cell order**. This is the "selection becomes a document" mapping that S13
    and S14 both reuse.
  - `pixlay-core` gains the **selection policy** as pure functions (no GTK, no filesystem): the ordered
    photo list, the 2..=9 clamp, the layouts that survive a count (`templates` filtered by
    `template.slots.len()`), and the LIFO add/remove rule against a `CollageDoc`. Putting it in core is
    what lets S13/S14 share one implementation and what keeps its tests display-free.
- **Exit criteria**:
  - `scan`'s JSON field set is fixed and asserted; two runs on the same directory are byte-identical;
    a fixture directory (PNG, JPEG, HEIC, 16-bit PNG, an EXIF-Orientation-6 file, a non-image, an
    unreadable file) produces exactly the expected rows, reasons and exit codes; the reported size of the
    orientation-6 file is the **rotated** one.
  - `init --photo` N times gives N cells whose sources are the arguments in order; N outside 2..=9 is
    refused naming both bounds (`EXIT_USAGE`); a template whose slot count differs from N is refused
    naming both numbers.
  - the LIFO rule is asserted on the document: a remove clears the last occupied cell and nothing else,
    the other cells keep photo, crop and grade; the add restores it in place.
  - `thumb`'s output has the requested long edge and its cost is recorded — **this is the picker's budget
    number** (`VmHWM` and wall clock, per `AGENTS.md`'s measurement rules).
- **Not doing**: no on-disk thumbnail cache, no XDG thumbnail-spec integration, no recursion into other
  mounts, no EXIF writing, no directory watching.
- **Human**: none.

### S9 · Result (2026-09-22)

**All four exit criteria are green**, and each one is a test rather than a claim:

- **`scan`** — `crates/pixlay-cli/tests/cli.rs::scan_lists_a_folder_of_photos_one_row_per_file` and
  `scan_reports_a_file_it_cannot_decode_as_a_row`. The field set is fixed per status (`path` + `status` +
  `mime`/`width`/`height`/`date`/`mtime` for one that decoded; `path` + `status` + `reason` for one that
  did not — no numeric fields to misread), the order is lexical by path, and two runs over an unchanged
  directory are byte-identical. The built fixture folder holds the six committed photo kinds (PNG, JPEG,
  HEIC, 16-bit PNG, EXIF-Orientation-6, dated) plus a non-image with a photo extension, a dangling
  symlink, a text file and a subdirectory, and the test builds it from the committed `photos/` rather
  than committing new binaries. `count = 8`, `failed = 2`, exit 0: a refusal is a row, not a skip and not
  a command failure. `oriented-6.jpg` (stored 600x1200) reports **1200x600** — the size after EXIF
  rotation — and `dated.jpg` reports `2019:07:14 10:32:00`. `--recursive` is the only way into a
  subdirectory.
- **`init --photo`** — `init_photo_writes_the_arguments_as_cells_in_order`: three arguments give three

**Decisions this step made** (recorded in `docs/CONTRACT.md` §5's S9 block):

- **`--photo` is repeatable**, and `image` / `thumb` refuse a second one. The alternative — a second flag
  for `init`'s list — would have given the surface two spellings of the same thing.
- **`scan` filters by extension** (`PHOTO_EXTENSIONS`, ten photo formats, case-insensitive) rather than
  attempting every file: reporting every `.txt` and `.pixlay` as a decode failure would make a folder's
  README into an error row. A file whose extension *is* a photo format and which fails to decode is a row
  with its reason, and the command still exits 0. `--help` documents the same list, and a test fails if
  the two drift.
- **`scan` decodes the frame**, not just the loader's early metadata: `ImageDetails`' dimensions are
  glycin's own "often correct, for an early rendering estimate" — not post-rotation — and the whole point
  of the row is the size a tile is laid out against.
- **`scan` reports `mtime` and paths**, which `AGENTS.md` and §5 otherwise forbid in a result. The rule
  exists so output cannot change between runs, and a directory listing's modification times are part of
  its input rather than contamination; two runs over an unchanged directory are still byte-identical.
  `mtime` is the key S12's decode cache invalidates on, so a caller that cannot see it would have to
  re-stat the filesystem to trust the answer.
- **A preview is written at 72 dpi**, and the second `resample`-shaped entry point (`thumb::thumbnail`)
  goes through the *existing* `resample` + `over_white` + quantize, so the picker's preview and a slot's
  bitmap are the same picture of a file, not two implementations.
- **`init --photo` refuses a photo that is not there** (exit 2) rather than writing a project that cannot
  be rendered; `Project::sources` already makes a missing photo a loud failure, and a document written on
  purpose should not be the one exception.
- **`Selection::new` does not enforce the floor**: the tray legitimately holds 0 or 1 photo while the user
  is picking, so the ceiling fires on `push` and the floor when a selection becomes a document. Without
  that split, S13's Next button (insensitive below two) would have no way to hold an incomplete selection.
- **No new dependency**, and no `Cargo.lock` change (the `cargo update --workspace` at the start of the
  step locked 0 packages).

## S11 · Free rotation, and the frame

**Goal**: ruling 11's free rotation, and stage 6's border/radius/colour — the two contract changes of
this plan.

- **Work**:
  - **Free rotation.** `MAX_ROTATION_DEG` (45°), `CLAMP_ZOOM_LIMIT` (1.5) and `CropFit::rotation_limited`
    with its `widest_rotation` machinery are **removed**. The fit keeps its one job: raise the drawn zoom
    to the value that covers the visible cell at **exactly the requested angle**, never reducing the
    angle. `rotationDeg` accepts any finite value and is normalized to `(-180, 180]` at validation, so a
    dial does not accumulate thousands of degrees in a project file. Old projects stay valid (a widened
    range accepts every value the cap allowed), so `DOC_VERSION` does not change.
    Two facts make this safe and they are the step's probes, not assumptions: the required covering zoom
    as a function of the angle is bounded on `[0°, 90°)` for every slot shape (its worst case is on the
    diagonal, and for the widest shipped slot — a ten-column strip with a 4:3 photo, which S3 measured at
    6.0× upright — the free angle takes it to the order of ten, three orders of magnitude below
    `MAX_ZOOM = 1000`), and **the bitmap's size does not follow the zoom** (a slot's bitmap is the slot's
    own pixel extent, so a larger zoom resamples a smaller source region into the same output — it costs
    less, not more, and S0/S7's memory budget is untouched).
  - **The frame.** `CollageDoc.frame: { gapRel, radiusRel, color }` with serde defaults `0`, `0`, white:
    no version bump, and every existing project renders byte-identically. Both lengths are fractions of
    the canvas **height**, like a text layer's `sizeRel`.
  - **The geometry it implies**, stated once so no session has to re-derive it:
    - the *visible* area of a slot is `slot.outline ∩ rounded_rect(slot_bbox inset by gapRel/2, radiusRel)`
    - the fit's reference becomes the **inset bounding rectangle** (a rectangle, so S3's math is
      unchanged): everything visible lies inside it, so covering it covers the cell, and this is exact
      for a concave slot as well;
    - `radiusRel` is clamped to half the smaller side of the inset rectangle, and `gapRel` is refused
      when the inset would leave a cell empty (the error names the slot);
    - the clip path is the intersection above, so a rounded corner shows the backdrop, not a stretched
      photo.
  - **The decoration stage** in `render::draw`: the canvas is filled with `frame.color` (white by default)
    where it used to be hard-coded white in `draw` and in `probe`; the stage sits after slot compositing
    and before the text layers, which is where the frozen evaluation order already puts "canvas
    decoration".
  - **CLI**: `render --gap … --radius … --border-color …`, and an `edit` subcommand
    (`--slot <i> --rotate <deg> --zoom <z> --offset <x> <y> --clear --out <file>`) so slot transforms can
    be set, and therefore checked, without a window.
- **Exit criteria**:
  - **byte-identity**: a document with no `frame` renders byte-identical to the build before this step
    (the probe's pixels, not an eyeball);
  - **the sweep**: for a grid of angles (including ±180° and the diagonals), zooms, offsets, slot shapes
    and photo aspects, the clamped photo covers the entire visible cell to 1e-6 — the S3 sweep kept, with
    the cap gone and the reference rect in place;
  - **the numbers**: the required covering zoom per (slot, photo) aspect as a function of the angle, its
    worst angle, and the A0 memory/time budget re-measured at that worst angle;
  - **the frame is real**: at `radiusRel > 0` the corners' backdrop-coloured pixel count is > 0 and
    monotone in the radius; at `gapRel > 0` the seam is the requested width in pixels (a probe, not a
    look); with a coloured frame those pixels carry exactly that colour;
  - **grading identity** still pixel-identical; **`.pixlay` round-trip** keeps `frame` and the free
    rotation; **no test still asserts the ±45° cap** (they are replaced by the sweep);

**The blur, diagnosed and measured.** Two defects, and they multiply:

1. The pane's decode was the constant `PREVIEW_PX` = 1024 long edge. This machine's display is **3840x2160**
   (`/sys/class/drm/*/modes`, read 2026-09-22), so a maximized window asks the pane for up to **3.7x** that
   decode.
2. The pane can fall back to a **256 px tile** and stay there. `show_focused` paints the tile whenever one is
   in hand, and `Thumbs::seen` refuses a repeated `(index, preview)` request — so a photo that is focused,
   left and focused again shows its tile for as long as that record lives, and a folder change keeps the
   stale record, because the key has no folder in it. S13's own criterion — the pane against
   `pixlay-render thumb --px 1024` — passes, because it measures a *first* focus.

What a pane-sized decode costs, measured (`--release`, this machine, 2026-09-22, `thumb --photo
landscape.jpg`, wall clock including the ~25 ms process start):

| long edge | time |
|---|---|
| 1024 | 229 ms |
| 2048 | 593 ms |
| 3840 | 1112 ms |

So the fix is "decode at the pane's own device pixels, capped", and these are the numbers the cap buys: at
`PREVIEW_MAX_PX` = 2048 a maximized window is upscaled at most **1.9x** and one focus costs at most **0.59 s**,
where 3840 would cost 1.11 s per photo in a stage whose question is "is this the photo I meant".

### The GTK findings this step rests on (measured, 2026-09-22)

Three of them are why the code looks the way it does, and each one was found by measuring rather than by
reading:

1. **GTK binds more items than it shows, and never trims.** A fresh model in a 536x396 viewport binds
   **257** items — the same 257 for 300 photos and for 1000, so it is a constant of GTK's item manager,
   not a function of the folder. "Bound" is therefore not "visible", and the requests follow the screen:
   [`Picker::visible`] intersects the cell's allocation with the scroller's. Two traps inside that test:
   a bound cell that has not been allocated answers `compute_bounds` with its CSS border alone (a 6x6
   rect at (-3,-3), which intersects), and a scrolled list inside a `GtkPaned` is allocated its whole
   *content* when `shrink-end-child` is left at its default, which makes GTK count every item as
   visible. Both are commented where they are handled, with the number.
2. **A request's identity has to carry the folder generation.** The first implementation keyed a request
   by `(kind, index, px)` and dropped a reply whose generation was stale; a *stale* queued job then
   revived the *new* request's key, so the new job was skipped as already answered while its own reply
   was rejected as stale. Measured: six tiles stayed "in flight" for the whole three-minute wait on a
   folder of fourteen photos. `crate::thumbs`' `Key` now includes the generation, and the picker clears
   a reply's *own* in-flight entry before judging whether the answer is still wanted.
3. **The cell's waiting state is a static icon, not a spinner.** A mapped `GtkSpinner` animates even when
   it is clipped away, and GTK keeps 257 cells bound: the ones that are never asked for would spin for as
   long as the folder is open. `image-loading-symbolic` says the same thing and costs nothing.

**Decisions this step made** (all recorded in `docs/CONTRACT.md` §9):

- **`shrink-end-child(true)` on both dividers**, with the reason and the number in the code: it is the
  difference between a grid that is 396 px tall and one that is allocated 300 photos' worth of rows.
- **The pane's "current" state is a thing the layer can be held to** (`Picker::preview_current`): before
  S13b the pane could be showing a tile, or another photo's preview, and nothing named that state, so
  nothing could fail on it.
- **A picture is one buffer, not two** (`Rc<Picture>` in both caches: the `glib::Bytes` the texture reads
  and the texture itself), and painting from a cache is a refcount bump rather than a copy of the pixels —
  S13 copied the whole image on every paint, which for a 9.4 MB preview is a copy per frame.
- **The stylesheet is loaded from the binary** (`include_str!("style.css")`) and installed at
  `GtkApplication::startup`, not at build time: the display does not exist until GTK has initialised.
- **`gtk4`'s feature level moves to `v4_12`** (`Cargo.toml`, and the dependency registry in `AGENTS.md`):
  `GtkListBox::remove_all`, `GtkCssProvider::load_from_string` and — the one that is a real requirement —
  `GdkSurface::layout`, GTK4's only "the window was resized" signal. Below 4.12 the build would compile
  and the preview pane would never follow a resize.
- **Ruling 2's "zoom and pan" stays the editor's**: the stage's preview is `Contain`-fitted and static,
  as S13 read it, and the ruling did not change it.

**Human**: none. The ruling above is the human's input, and the stage's *look* — 256 px cells, a drag that
lands where the hand expects, an arrangement that reads — is judged at S15's walk
(`docs/HIG-REVIEW.md` §2, steps 1–3), which is where S13's three questions went too.

### The decisions this step made

- **The strip is a horizontally-reflowing `GtkGridView`**, `min_columns = max_columns = 1`, inside a scroller

  orientation is the axis items flow along, and one item per vertical slice makes the row single at any
  widget height. It also bounds GTK's live cells at `30 × max_columns` = 30 (`gtkgridview.c`), which is why
  a 300-photo folder's requests drop from S13b's 17 to 9.
- **`TILE_SIZE` is the cell's *image*, not its slot.** A cell's allocation is 128 + the 1 px CSS border, its

  wants; a copy *at* the candidate's size is read at 1:1, where the reduction's own sampling is the

- **The gallery is one more job on the canvas's decode worker, and the worker coalesces per kind.** The
  band is rebuilt on every committed edit, so a queue that kept only the newest job of *any* kind would drop
  the canvas's bitmaps for a thumbnail nobody asked to look at. Two jobs, two generations, canvas first —
  which is also what puts the preview-grade copies in the cache before the band reads them.

  so a shorter placeholder means the canvas is laid out twice on every open — one more grid and one more

document — and the `Export…` dialog, keeping the "the export call returns immediately" claim it has always
made.

**Three defects in the window and in the test harness were found while the suite ran, and all three are
fixed where they belong.** (1) **The editor's canvas now reads its size from the surface**, not only from its own draw:
`editor_page.connect_realize` → `GdkSurface::layout` → `request_grid_for` + `refresh`, the hook the picker's
pane has used since S13c. GTK4 has no `size-allocate`, and a page that has just been pushed is *allocated
before it is painted* — a run in which the paint never came left the canvas on a 1x1 grid and the whole
editor page unmeasured for the length of the test (measured: the HIG walk read a 0x0 canvas, a band with no
candidates and header controls at position 0 on some runs of four, and was fine on the others). (2) **The
window's test-facing waits pump a frame before they poll** (`EditorWindow::pump_until`): the work they wait
for is requested by the first draw that knows the widget's size, so a wait that only reads its flags can
return before the work exists. (3) **`tests/support::allocated` / `::canvas_size`** wait for the frame that
allocates a widget that has just been shown or added by a worker's reply — the band's candidate cells and
the cell controls both arrive that way, and a wait that stops at the reply can measure them one frame too
early (measured: candidate cells of 0x0 on two runs of four). `tests/support::close_dialog` carries the
fourth measurement, which is a *limit* rather than a fix: a headless X server never finishes an
`AdwDialog`'s close transition, so the harness forces the dismissal after the app's own `close()` has been
accepted — and a widget behind a *presented* dialog snapshots to nothing, which is why the frame's pixel
probe is taken with the dialog out of the way.

**A pane too narrow for the row gets a column.** The strip's five 32-px controls are 186 px long, and the
library's narrow panes are 61–122 device px wide at the default window (measured 2026-09-23: a 1/16 column
of the 16:9 sheet is 61, `strip-9-9x1`'s panes 122): a row there would have started at the cell's left edge
and covered the neighbouring photo, taking its clicks. The same five controls stacked need
32 px across and 176 down, which those panes have, so `CellControls::sync_in` turns the strip
(`GtkBox::set_orientation`) and places it at the cell's right edge instead. Measured 2026-09-23: the column
is **34x186** inside one of `strip-9-9x1`'s panes (60,12–182,563), and the row stays **186x34** inside a
3/8 x 3/8 cell — so "the buttons sit inside the selected slot's rectangle" holds for every cell in the
library, which is what the criterion asked and what `tests/compose.rs` asserts of both shapes.

**What no test can press, and the walk must**: the two `GtkFileDialog` choosers — the platform's own
dialog, which no test can answer; the controls are held to being named and reachable, and the human presses
them. Whether a column of five buttons reads as well as the row is the walk's look, and it is on the list
in `docs/HIG-REVIEW.md` §2.

### The decisions this step made

1. **`Frame…` applies as it moves and has no affirmative.** A dialog whose rows have already changed the
   document has nothing to confirm, and a Cancel would have to unwind a stack of live edits — a second
   undo stack, which is the thing ruling 26 refused for `+`. So the rows are the *gesture* path
   (`EditorWindow::set_frame` keeps the command pending and the quiet commit makes it one step) and the
   dialog's one button is *Close*. HIG's action-dialog advice is followed for the dialog that *is* an
   action (`Export…`: Cancel then Export, the verb on the affirmative).
2. **The two lengths are per cent of the collage's height in the dialog**, fractions in the document. A row
   is a number a person types: "4" reads as a share where "0.04" reads as a mystery, and the conversion
   lives in one place (`dialogs.rs`'s `PERCENT`). The group's description carries the unit once instead of
   both rows repeating it.
3. **The rotate control steps 15°, and the wheel keeps 1°.** The angle is free (S11) so a button has to
   pick a step; 15° makes six presses a quarter turn and is still fine enough to straighten a hand-held
   horizon, and the wheel's 1° stays the fine control on the same axis. It is a *step*, not a cap: nothing
   in the document is limited by it.
4. **The strip is one widget, not one per cell.** Nine cells × five buttons would be 45 widgets and 45
   closures doing five edits; the handlers ask the window which cell is selected. The `+`s stay per slot
   because they *are* per-slot controls (each asks for its own cell's photo).
5. **`EmptyCells` became `CellControls`.** The layer now holds two families, and the name says what it is
   rather than what it started as.
6. **Clear is one command** (above): `Command::ClearCell`, so the CLI flag, the strip's button and the
   canvas's `Delete` mean one thing and one press is one undo step.
7. **The frame became a command** (above): `Command::SetFrame`, the one writer for both surfaces.
8. **The window's tooltips stay sentence case.** HIG `patterns/feedback/tooltips` asks for header
   capitalization; every tooltip in this window has been a sentence since S7, and changing some of them now
   would leave the window inconsistent. Recorded in `docs/HIG-REVIEW.md` §1 as a deviation with its landing
   point: the copy pass belongs with S16's translation work, which re-reads every string anyway.

### S15b · landed (2026-09-24)

The first batch, done first for the reason the section's order gives, and closed on its own measurement.
The mechanism behind the `0x0` the review reported is in the window rather than in the test:

- `on_decoded` installed the bitmaps and never re-synced the cell controls, while the other sync sites
  (`refresh` from a surface layout, an edit, a selection) are not guaranteed to follow that reply.
- `CellControls::sync_in` placed against whatever `images` held — including the window's `1x1`
  placeholder, now named once as `PLACEHOLDER_GRID` and used by the reset, the reply's fallback and the
  guard — and `placement` stretches that single texel over the whole widget, so the margins it produced
  were a placement of a sheet that does not exist.

**The fix**: `sync_in` places nothing against a placeholder grid or an unallocated canvas (it hides the
controls instead), and `on_decoded` syncs once the real grid is installed. The test side asks for the
*condition* rather than a longer sleep: `support::canvas_bitmaps` waits for the canvas's bitmaps to be in
hand **for the grid it rests at** (`support::canvas_size` answered "has a size and nothing in flight",
which a placeholder grid also satisfies), and `tests/compose.rs` now selects a cell **before** the first
frame is pumped and never calls `sync_in` itself, so what it measures is the production path.

Measured (2026-09-24, session display — this machine has no `xvfb-run`, so the GUI tests ran against
`:0`/Wayland rather than the headless path the repository's own notes are from):

| | |
|---|---|
| the new assertion with the guard and the re-sync reverted | **FAILED in 0.52 s** — "no control is placed before its bitmaps are in hand" |
| the same assertion with the fix | passed; **68.02 s** for the whole test |
| a full `cargo test` before any of this | green, **255 s** — the review's PIX-020A did not reproduce as it described it |

**The rest of the red was the session display, and it was measured, not guessed.** With the wait's
failure message carrying the window's own frame count, one 180 s timeout reported
`91 frames, active false, mapped true, last canvas draw refusal: None`: a window the compositor has stopped
compositing is sent almost no frame callbacks, and GTK lays out and caches render nodes only on a frame, so
every allocation, orientation and pixel the tests read is a stale one until the next frame arrives — which
on a background window can be seconds. A bare window on the same machine, unfocused, ticked at **121 frames
in 2 s** a moment earlier, so this is the window's visibility and not the machine.

Three waits, three conditions:

- **`pump` asks for the window again** after `FRAME_STALL` (2 s) without a frame, which is what puts a
  background test window back in front of the session.
- **Every wait says what it saw** on timeout: `support::frame_state` (frames, active, mapped, the canvas's
  last `render` refusal) is in the messages of `allocated`, `canvas_size`, `canvas_bitmaps`, `snapshot` and
  both of `tests/compose.rs`'s own waits. A timeout that cannot name its cause is the flake this batch is
  about.
- **A pixel probe waits for its own observation.** GTK hands a snapshot the widgets' *cached* render nodes,
  so a probe taken before the frame carrying the change reads the previous picture — measured twice: a
  pick/unpick probe comparing two identical images (RMSE 0.000), and a frame-junction probe reading
  `[255, 230, 230]` where `[255, 0, 0]` was due because two *window* frames had passed without the canvas
  being redrawn. `support::settle_by` polls the observation (bounded by `PROBE_WAIT`, 60 s) and the assert
  still runs on what came back, so an observation that never arrives fails as it did before.
  `support::close_dialog` waits for the dialog to stop being visible rather than for 200 ms.

## S16 · Packaging

**Goal**: get into AUR — the retired S8, moved here by ruling 6 so it packs the product that exists.

- **Work**: `PKGBUILD`, a desktop file, icons, a dependency list; the translations under `po/` and the
  multilingual fields of `.desktop` / metainfo.
- **Exit criteria**: `cargo vendor` passes and `cargo build --frozen --offline` passes; `makepkg`
  succeeds in a clean chroot; the desktop file and icons pass validation; **the installed package starts
  and walks the new main path**; `msgfmt --check` passes; with no language pack the interface is English.
  `check()` runs the fast tier only (heavy tests are `#[ignore]`d or feature-gated) and must work offline:
  a clean chroot has no font cache, no `$HOME` and no display, which is what the `xvfb-run` idiom in
  `tests/support/mod.rs` already covers.

- **Human**: the "the installed package walks the path" criterion, verified on the built package.
