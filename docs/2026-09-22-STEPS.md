# Pixlay implementation steps

**This plan began on 2026-09-22** (the commit that added this file), and that is the date in its name.
It replaces the plan of 2026-09-20, which is retired — its text, S7's implementation and its void human
walk are in [`docs/archive/2026-09-20-STEPS.md`](archive/2026-09-20-STEPS.md). The review that produced
this plan is [`docs/2026-09-22-UX-DIRECTION.md`](2026-09-22-UX-DIRECTION.md): it holds the target flow,
the evidence against forking Loupe, and the rulings below in their original wording.

**The S-numbering continues** from the retired plan (which ended at S8) so that the S1…S7 citations
already written into code comments keep resolving: S9 is the first step here.

Run the steps in order. **One step at a time**; finish a step before starting the next.

The first sentence for a new session:

> Read `AGENTS.md`, then read `docs/2026-09-22-STEPS.md`. Do only the step the "Current progress" line under "Status" points at, and do not start later steps ahead of time.
> After finishing a step, run that step's verification command, turn its exit criteria into tests, write the outcome into that step's "Result" subsection, then update its status row and the "Current progress" line.

- Hard constraints and invariants are in `AGENTS.md`; this file only orders the steps and gives the exit
  criteria, and does not repeat their content. The measurement rules, and how a constant's source is
  annotated, are in `AGENTS.md` too ("Verification entry").
- How the steps are split, and the three cases in which a step must end a session, is `AGENTS.md`'s
  "Step discipline".
- Before starting a step, run `cargo test` once to confirm the baseline is green.

- **Flip is out of scope, and so is any quarter-turn field.** The retired plan's `AGENTS.md` line

## Ruling (2026-09-22, human): the purity cut

Asked to make the product **only** a photo collage, the human ruled four things out of it. Each one is a
removal, not a change of behaviour, and together they take S12c.

| # | Question | Ruling |
|---|---|---|
| 13 | Canvas-level text layers (S5), the tiled watermark included | **Removed.** No text of any kind: no layer, no watermark, no `{date}` / `{filename}` / `{index}` token, no `textFallback`. |
| 14 | Per-slot grading and the one-click canvas-wide filter (S4) | **Removed.** A collage places photos; it does not colour them. |
| 15 | The ten-slot recipe (`strip-10-10x1`) and `MAX_SLOTS` | **Removed.** Ruling 3's cap is 9, so a ten-slot layout was already unreachable from every surface; it stops being expressible at all. |
| 16 | Output formats and the export form | **PNG and JPEG only** — TIFF goes, and with it the JPEG `--chroma` flag. The window's export form keeps **one quality option** (the export resolution); the sheet size stays a document field, reached from the CLI. |

The basis, in the order the cuts pay for themselves:

1. **None of it is on the main path.** Ruling 12's path is `open → pick 2–9 photos → pick a layout → adjust →
   export`, and the human's own stage list has no text (`docs/2026-09-22-UX-DIRECTION.md` §9 puts "poster mode
   (presets + text styles)" out of scope). Grading is an editor's control in a product whose per-cell
   capabilities ruling 11 fixed as *zoom, move, rotate*.
2. **Text is the one feature whose pixels depend on the host.** `pixlay-render` asks fontconfig for the generic
   `sans-serif` (`crates/pixlay-render/src/text.rs`), so the same document renders differently on two machines —
   against `AGENTS.md`'s "identical input yields identical output". The measurements only looked reproducible
   because the tests pin a font through `FONTCONFIG_FILE`.
3. **Each cut removes a dependency or a whole pipeline stage.** Text takes `pangocairo` (and the `pango` chain)
   out of `pixlay-render`; TIFF takes `tiff`/`weezl` out of `pixlay-imaging`; grading takes one of the two
   colour stages out of the frozen evaluation order.
4. **A document field is cheapest to remove now.** `CollageDoc` is read with `deny_unknown_fields`, so deleting
   `text` / `filter` / `textFallback` / `grade` refuses every project a previous build wrote. That is why
   `DOC_VERSION` moves to 2 for this cut, and why it happens *before* S16 packaging: once S16 has shipped, a
   `.pixlay` in a user's home turns the same cut into a migration decision.

## Ruling (2026-09-22, human): pixels, not paper

Asked where an export's size comes from — a physical canvas times a resolution, or a pixel count — the
human ruled, verbatim: **"从来没有要过纸这个概念。都是你瞎编。直接用像素控制。"** ("The concept of paper
was never asked for. You made it up. Control with pixels directly.") Pixels are the only size the product
knows, and S12d executes it. This **amends ruling 16**: its clause "the sheet size stays a document field,
reached from the CLI" is exactly what is overruled — `edit --sheet` and the field it set go with it.

| # | Question | Ruling |
|---|---|---|
| 17 | Where does an export's size come from: a physical canvas × a resolution, or pixels? | **Pixels only.** `CollageDoc` loses its `canvas` field; millimetres, DPI and every conversion between them leave the code, the flags and the files; **one pixel count (the long edge)** sizes every render, and the window's quality row is that number. |

The basis, in the order the cut pays for itself:

1. **A raster's only intrinsic size is pixels.** Millimetres × dpi is a print instruction layered on top
   of pixels — the same file prints at whatever size its reader divides it by — and this product was
   never asked to speak for a printer. Paper entered as scaffolding: S0's performance spike measured an
   A0 render, and S6 made the file carry the resolution it was asked for. Neither made paper part of what
   a document *is*, and ruling 16's `edit --sheet` (2026-09-22, this morning) kept the concept alive one
   step longer than it was ever requested.
2. **It deletes the last cross-field consistency rule.** "The canvas's aspect must equal the template's"
   existed only because two fields each described the same shape; the export grid's shape *is* the
   template's, so the mismatch becomes unrepresentable instead of validated.
3. **It collapses the export surface to one number.** The window's quality row, `render`'s size flag and
   `probe`'s grid all become the same long-edge pixel count: no conversion, no rounding rule to freeze,
   and no resolution in a file that nobody chose.

## Ruling (2026-09-22, human): no utility pane

Asked whether the sidebar still earns its place once every group it holds has a home elsewhere, the
human ruled it does not: the pane goes, and an `Export…` dialog carries the three export questions.
Verbatim: "输出可以在点击Export的时候出一个对话框，选择格式、输出质量、文件名（带选择路径）。"
("Exporting can pop a dialog when Export is pressed: format, output quality, filename with a path
chooser.")

| # | Question | Ruling |
|---|---|---|
| 18 | The utility pane (`AdwOverlaySplitView` + `AdwPreferencesPage`, the Template / Photo / Framing / Export groups) | **Removed, in the UI steps that own its groups.** Each group already has a home: the template combo becomes S14's candidate gallery, the photo buttons are S13's picker plus S14's add/remove and S15's replace/clear, framing is S15's floating buttons plus the gestures, and export becomes the `Export…` dialog below. What has no other home — the frame's gap/radius/colour — moves into a small `Frame…` dialog of the same shape rather than keeping the pane alive for three rows. |

The basis:

1. **A linear three-minute flow has no use for a permanent panel.** The pane was the editor's
   instrument board; the product is now `pick → layout → compose`, and each stage owns its own
   controls (the tray, the gallery, the floating buttons, the dialog). Keeping the pane would mean
   maintaining two surfaces for every one of those decisions.
2. **The export dialog is the standard shape, not an invention.** GTK4's `GtkFileDialog` takes no
   custom widgets, so format + quality + filename-with-path-chooser as rows of an `AdwDialog` is
   the platform's own answer — the same shape the unsaved-changes confirmation already uses.
3. **The frame dialog is the same shape for the same reason.** Three normalized rows behind a
   header-bar `Frame…` button on the compose stage, like `Export…`: one pattern for both
   document-level questions, neither of them a permanent row.

## S9 · Library and selection on the CLI — ✅ done (2026-09-22)

**Goal**: stages 1–2 of the flow exist as machine surface, so the picker's pixels and its cost can be
measured without a window (`AGENTS.md`: nothing may be possible only in the GUI).

- **Work**:
  - `pixlay-render scan --dir <path>`: the image files of a directory as JSON — path, mime type, size
    *after* EXIF rotation, the EXIF date when there is one, and `mtime`; ordering is lexical by path and
    stable across runs; a file the decoder refuses is a row with its reason, not a silent skip. No
    recursion unless `--recursive`.
  - `pixlay-render thumb --photo <path> --px <n> --out <file>`: one thumbnail's pixels as a file, so the
    picker's expensive half is a CLI number (`AGENTS.md`: a visual conclusion must become a number).
  - `pixlay-render init --template <name> --photo <p>… --out <file>`: extends the existing `init` with
    photos, **argument order = cell order**. This is the "selection becomes a document" mapping that S13
    and S14 both reuse.
  - `pixlay-core` gains the **selection policy** as pure functions (no GTK, no filesystem): the ordered
    photo list, the 2..=9 clamp, the layouts that survive a count (`templates` filtered by
    `template.slots.len()`), and the LIFO add/remove rule against a `CollageDoc`. Putting it in core is
    what lets S13/S14 share one implementation and what keeps its tests display-free.
- **Exit criteria**:
  - `scan`'s JSON field set is fixed and asserted; two runs on the same directory are byte-identical;
    a fixture directory (PNG, JPEG, HEIC, 16-bit PNG, an EXIF-Orientation-6 file, a non-image, an
    unreadable file) produces exactly the expected rows, reasons and exit codes; the reported size of the
    orientation-6 file is the **rotated** one.
  - `init --photo` N times gives N cells whose sources are the arguments in order; N outside 2..=9 is
    refused naming both bounds (`EXIT_USAGE`); a template whose slot count differs from N is refused
    naming both numbers.
  - the LIFO rule is asserted on the document: a remove clears the last occupied cell and nothing else,
    the other cells keep photo, crop and grade; the add restores it in place.
  - `thumb`'s output has the requested long edge and its cost is recorded — **this is the picker's budget
    number** (`VmHWM` and wall clock, per `AGENTS.md`'s measurement rules).
- **Not doing**: no on-disk thumbnail cache, no XDG thumbnail-spec integration, no recursion into other
  mounts, no EXIF writing, no directory watching.
- **Human**: none.

### S9 · Result (2026-09-22)

**All four exit criteria are green**, and each one is a test rather than a claim:

- **`scan`** — `crates/pixlay-cli/tests/cli.rs::scan_lists_a_folder_of_photos_one_row_per_file` and
  `scan_reports_a_file_it_cannot_decode_as_a_row`. The field set is fixed per status (`path` + `status` +
  `mime`/`width`/`height`/`date`/`mtime` for one that decoded; `path` + `status` + `reason` for one that
  did not — no numeric fields to misread), the order is lexical by path, and two runs over an unchanged
  directory are byte-identical. The built fixture folder holds the six committed photo kinds (PNG, JPEG,
  HEIC, 16-bit PNG, EXIF-Orientation-6, dated) plus a non-image with a photo extension, a dangling
  symlink, a text file and a subdirectory, and the test builds it from the committed `photos/` rather
  than committing new binaries. `count = 8`, `failed = 2`, exit 0: a refusal is a row, not a skip and not
  a command failure. `oriented-6.jpg` (stored 600x1200) reports **1200x600** — the size after EXIF
  rotation — and `dated.jpg` reports `2019:07:14 10:32:00`. `--recursive` is the only way into a
  subdirectory.
- **`init --photo`** — `init_photo_writes_the_arguments_as_cells_in_order`: three arguments give three
  cells whose `source` values are the arguments in order (stored relative to the project file, and
  `elsewhere/…` when the photos are in a sibling directory), the project loads back with every photo
  resolving, and it renders with `occupied = 3`. `init_refuses_a_photo_count_outside_the_range_or_a_wrong_slot_count`:
  1 and 10 photos are exit 1 naming **`2..=9`**, three photos into a two-slot template is exit 1 naming
  the template and both counts, a missing photo is exit 2 naming it, and none of them writes a file. The
  photo-free project of S2 is unchanged (`photos = 0`).
- **The LIFO rule** — `crates/pixlay-core/tests/selection.rs`, nine tests in `pixlay-core` (no display, no
  filesystem): `remove_last` clears the last **occupied** cell with a hole in the middle of the document,
  leaves the other cells' photo, crop and grade untouched, and `Removed::restore` is the exact inverse
  (`assert_eq!(doc, before)`), refusing a cell that has been taken or that no longer exists. The same file
  asserts the ordered list, the 2..=9 clamp (with `strip-10-10x1` in the library and never offered) and
  `layouts()` against `templates::all` filtered by slot count, so the count filter cannot drift.
- **`thumb`** — `thumb_writes_a_preview_at_the_requested_long_edge`: the long edge is exact
  (100x50 from 400x200, 256x128 from the 600x1200 file it displays as 1200x600), every pixel of a flat
  photo comes back within one level, `pHYs` is 2835 px/m (72 dpi), and `--stats` carries the budget
  number. `crates/pixlay-imaging/tests/thumb.rs` adds the cases no fixture can: an exact ratio, an
  upscale, a 10000x1 pillarbox, alpha flattened onto white, a ramp that must not be cropped, and the
  independent check — the preview of `resample-source.png` at 200 px against ImageMagick's committed
  reduction (`resample-lanczos-200.png`).

**Measured** (2026-09-22, `--release`, recorded in `docs/CONTRACT.md` §8 "S9"): `scan` of a 14-file
folder **ms 190–194 / `peak_rss_mb` 32.7** (~13.6 ms per file — opening a folder *is* the decodes);
`thumb --px 256` of a 1 MP photo **ms 49–50 + `encode_ms` 8.9 / `peak_rss_mb` 19.7**; `--px 1024`
ms 70–155 / 26.6–35.5 MB; and the whole CLI preview path is **1.51/255 RMSE** from ImageMagick's own
Lanczos reduction, measured with `magick compare` on the written PNG.

**Decisions this step made** (recorded in `docs/CONTRACT.md` §5's S9 block):

- **`--photo` is repeatable**, and `image` / `thumb` refuse a second one. The alternative — a second flag
  for `init`'s list — would have given the surface two spellings of the same thing.
- **`scan` filters by extension** (`PHOTO_EXTENSIONS`, ten photo formats, case-insensitive) rather than
  attempting every file: reporting every `.txt` and `.pixlay` as a decode failure would make a folder's
  README into an error row. A file whose extension *is* a photo format and which fails to decode is a row
  with its reason, and the command still exits 0. `--help` documents the same list, and a test fails if
  the two drift.
- **`scan` decodes the frame**, not just the loader's early metadata: `ImageDetails`' dimensions are
  glycin's own "often correct, for an early rendering estimate" — not post-rotation — and the whole point
  of the row is the size a tile is laid out against.
- **`scan` reports `mtime` and paths**, which `AGENTS.md` and §5 otherwise forbid in a result. The rule
  exists so output cannot change between runs, and a directory listing's modification times are part of
  its input rather than contamination; two runs over an unchanged directory are still byte-identical.
  `mtime` is the key S12's decode cache invalidates on, so a caller that cannot see it would have to
  re-stat the filesystem to trust the answer.
- **A preview is written at 72 dpi**, and the second `resample`-shaped entry point (`thumb::thumbnail`)
  goes through the *existing* `resample` + `over_white` + quantize, so the picker's preview and a slot's
  bitmap are the same picture of a file, not two implementations.
- **`init --photo` refuses a photo that is not there** (exit 2) rather than writing a project that cannot
  be rendered; `Project::sources` already makes a missing photo a loud failure, and a document written on
  purpose should not be the one exception.
- **`Selection::new` does not enforce the floor**: the tray legitimately holds 0 or 1 photo while the user
  is picking, so the ceiling fires on `push` and the floor when a selection becomes a document. Without
  that split, S13's Next button (insensitive below two) would have no way to hold an incomplete selection.
- **No new dependency**, and no `Cargo.lock` change (the `cargo update --workspace` at the start of the
  step locked 0 packages).

## S11 · Free rotation, and the frame

**Goal**: ruling 11's free rotation, and stage 6's border/radius/colour — the two contract changes of
this plan.

- **Work**:
  - **Free rotation.** `MAX_ROTATION_DEG` (45°), `CLAMP_ZOOM_LIMIT` (1.5) and `CropFit::rotation_limited`
    with its `widest_rotation` machinery are **removed**. The fit keeps its one job: raise the drawn zoom
    to the value that covers the visible cell at **exactly the requested angle**, never reducing the
    angle. `rotationDeg` accepts any finite value and is normalized to `(-180, 180]` at validation, so a
    dial does not accumulate thousands of degrees in a project file. Old projects stay valid (a widened
    range accepts every value the cap allowed), so `DOC_VERSION` does not change.
    Two facts make this safe and they are the step's probes, not assumptions: the required covering zoom
    as a function of the angle is bounded on `[0°, 90°)` for every slot shape (its worst case is on the
    diagonal, and for the widest shipped slot — a ten-column strip with a 4:3 photo, which S3 measured at
    6.0× upright — the free angle takes it to the order of ten, three orders of magnitude below
    `MAX_ZOOM = 1000`), and **the bitmap's size does not follow the zoom** (a slot's bitmap is the slot's
    own pixel extent, so a larger zoom resamples a smaller source region into the same output — it costs
    less, not more, and S0/S7's memory budget is untouched).
  - **The frame.** `CollageDoc.frame: { gapRel, radiusRel, color }` with serde defaults `0`, `0`, white:
    no version bump, and every existing project renders byte-identically. Both lengths are fractions of
    the canvas **height**, like a text layer's `sizeRel`.
  - **The geometry it implies**, stated once so no session has to re-derive it:
    - the *visible* area of a slot is `slot.outline ∩ rounded_rect(slot_bbox inset by gapRel/2, radiusRel)`
    - the fit's reference becomes the **inset bounding rectangle** (a rectangle, so S3's math is
      unchanged): everything visible lies inside it, so covering it covers the cell, and this is exact
      for a concave slot as well;
    - `radiusRel` is clamped to half the smaller side of the inset rectangle, and `gapRel` is refused
      when the inset would leave a cell empty (the error names the slot);
    - the clip path is the intersection above, so a rounded corner shows the backdrop, not a stretched
      photo.
  - **The decoration stage** in `render::draw`: the canvas is filled with `frame.color` (white by default)
    where it used to be hard-coded white in `draw` and in `probe`; the stage sits after slot compositing
    and before the text layers, which is where the frozen evaluation order already puts "canvas
    decoration".
  - **CLI**: `render --gap … --radius … --border-color …`, and an `edit` subcommand
    (`--slot <i> --rotate <deg> --zoom <z> --offset <x> <y> --clear --out <file>`) so slot transforms can
    be set, and therefore checked, without a window.
- **Exit criteria**:
  - **byte-identity**: a document with no `frame` renders byte-identical to the build before this step
    (the probe's pixels, not an eyeball);
  - **the sweep**: for a grid of angles (including ±180° and the diagonals), zooms, offsets, slot shapes
    and photo aspects, the clamped photo covers the entire visible cell to 1e-6 — the S3 sweep kept, with
    the cap gone and the reference rect in place;
  - **the numbers**: the required covering zoom per (slot, photo) aspect as a function of the angle, its
    worst angle, and the A0 memory/time budget re-measured at that worst angle;
  - **the frame is real**: at `radiusRel > 0` the corners' backdrop-coloured pixel count is > 0 and
    monotone in the radius; at `gapRel > 0` the seam is the requested width in pixels (a probe, not a
    look); with a coloured frame those pixels carry exactly that colour;
  - **grading identity** still pixel-identical; **`.pixlay` round-trip** keeps `frame` and the free
    rotation; **no test still asserts the ±45° cap** (they are replaced by the sweep);
  - `edit` is idempotent on the fit (applying it twice equals applying it once) — the property S3
    established must survive the signature change.
- **Not doing**: mirroring/flip in any form (ruling 11 — it is also added to `AGENTS.md`'s "not doing"
  list so nobody re-adds it), quarter turns as a field, per-cell border colour, backgrounds other than a
  flat colour, drop shadows, movable dividers.
- **Human**: none for the code; the frame's *look* is judged at S15.

## S12b · The preview-grade source — ✅ done (2026-09-22)

**All five exit criteria are green**, and each one is a test rather than a claim:

- **Next is gated by the floor and the cap is reported.** `picker.rs`'s test asserts Next insensitive at

  of the same photo differ by **RMSE 0.0218** over 1024x768 pixels (threshold 6) — the same

- **The grid fills progressively and the main loop never waits.** Opening the folder is a directory read
  of 14 files and returns before *any* tile exists — asserted, and it is a real property rather than a
  race: every tile arrives through `MainContext::invoke`, and the call iterates nothing. The tiles then

  (13 painted of 14 tiles at the snapshot).
- **Keyboard and language.** `tests/hig.rs` walks both stages: the picker's grid is backed by a

**Measured** (2026-09-22, debug profile, this machine — the tiles are decoded by the same code the
release build runs, so the numbers are the *shape* of the cost rather than its floor): a 14-photo folder

second. The S9 record's numbers (`thumb --px 256`: 49–50 ms, `VmHWM` 19.7 MB, `--release`) remain the
budget this stage was designed against.

**Decisions this step made** (recorded in `docs/CONTRACT.md` §9):

- **The picker owns the cell's click.** A `GtkMultiSelection` replaces its selection on a plain click
  (`gtklistfactorywidget.c`: `modify = Ctrl held`, so a plain click is `select_item(pos, unselect_rest =
  TRUE)`), which is the platform's own idiom and exactly wrong for "click three photos, get three". The
  cell claims the gesture and the picker toggles through the model, so the check marks, the model's
  `selected` state and the ordered list cannot disagree. `Ctrl+A` and `Esc` are the picker's own keys.
- **A decoded tile is handed to the cell that is showing it.** GTK does not re-bind a row because a
  texture arrived, and the item object must *not* be replaced (a multi-selection is keyed on it, so
  replacing an item would silently unpick that photo). The picker therefore remembers the picture each
  position is bound to and sets its paintable directly — a bug the first implementation had, found by
  looking at the stage's own screenshot rather than at a passing test.
- **The check mark is an indicator, not a control.** `.selection-mode` on a `GtkCheckButton` gives
  libadwaita's own round check, but with `can-target = false` and `can-focus = false`: the cell's click
  is the toggle, and a second control would either double-toggle or hide the click target.
- **The stage's preview does not zoom.** Ruling 2's "fit and zoom" is the photo filling the pane
  (`ContentFit::Contain`); magnification belongs to the editor's gestures, and a zoom control here would
  be a second place to get the canvas's own arithmetic wrong.
- **The export form's state moved into the window** (`EditorWindow::set_export_settings` /
  `export_settings`), and `MIN_EXPORT_PX` / `MAX_EXPORT_PX` moved to `export.rs`. Ruling 18 removes the
  pane that held the form, and S15 owns the `Export…` dialog that will be the rows over this state — so
  this step kept the capability and the test surface, and deleted the widgets.
- **The picker lists `XDG_PICTURES_DIR` on the first map**, not at build time: the page is worth listing
  only once it is on screen, and a window built by a test that never shows it should not walk the user's
  home directory.

**Human**: the three items this step's Work section names — the grid's density, how the selection reads,
whether the tray earns its space — are the picker half of S15's scripted walk (`docs/HIG-REVIEW.md`,
section 2, steps 1–2), which is the gate the table above owns. This step therefore closes on its Result,

**Open questions, written down rather than asked** (this session ran unattended, so every question a
human would normally be asked is recorded here and in the gate table instead):

1. **The grid's density.** The cells are 128 px squares with a 256 px tile behind them, which at the
   default 1100x760 window is three columns beside the preview. Is that the right number, or should the
   grid take more of the window and the preview less? (Section 2, step 3 of `docs/HIG-REVIEW.md` judges

2. **Whether the tray earns its space.** Each chip is a file name plus three small buttons (earlier,

3. **The preview has no zoom.** Ruling 2 says "grid + a large preview that can zoom and pan"; this step

5. **`Back` from the editor.** It keeps the document, so a user who goes back to change a photo and
