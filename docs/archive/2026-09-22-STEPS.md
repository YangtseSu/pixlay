## Ruling (2026-09-22, human): the purity cut

Asked to make the product **only** a photo collage, the human ruled four things out of it. Each one is a
removal, not a change of behaviour, and together they take S12c.

| # | Question | Ruling |
|---|---|---|
| 13 | Canvas-level text layers (S5), the tiled watermark included | **Removed.** No text of any kind: no layer, no watermark, no `{date}` / `{filename}` / `{index}` token, no `textFallback`. |
| 14 | Per-slot grading and the one-click canvas-wide filter (S4) | **Removed.** A collage places photos; it does not colour them. |
| 15 | The ten-slot recipe (`strip-10-10x1`) and `MAX_SLOTS` | **Removed.** Ruling 3's cap is 9, so a ten-slot layout was already unreachable from every surface; it stops being expressible at all. |
| 16 | Output formats and the export form | **PNG and JPEG only** — TIFF goes, and with it the JPEG `--chroma` flag. The window's export form keeps **one quality option** (the export resolution); the sheet size stays a document field, reached from the CLI. |

The basis, in the order the cuts pay for themselves:

1. **None of it is on the main path.** Ruling 12's path is `open → pick 2–9 photos → pick a layout → adjust →
   export`, and the human's own stage list has no text (`docs/archive/2026-09-22-UX-DIRECTION.md` §9 puts "poster mode
   (presets + text styles)" out of scope). Grading is an editor's control in a product whose per-cell
   capabilities ruling 11 fixed as *zoom, move, rotate*.
2. **Text is the one feature whose pixels depend on the host.** `pixlay-render` asks fontconfig for the generic
   `sans-serif` (`crates/pixlay-render/src/text.rs`), so the same document renders differently on two machines —
   against `AGENTS.md`'s "identical input yields identical output". The measurements only looked reproducible
   because the tests pin a font through `FONTCONFIG_FILE`.
3. **Each cut removes a dependency or a whole pipeline stage.** Text takes `pangocairo` (and the `pango` chain)
   out of `pixlay-render`; TIFF takes `tiff`/`weezl` out of `pixlay-imaging`; grading takes one of the two
   colour stages out of the frozen evaluation order.
4. **A document field is cheapest to remove now.** `CollageDoc` is read with `deny_unknown_fields`, so deleting
   `text` / `filter` / `textFallback` / `grade` refuses every project a previous build wrote. That is why
   `DOC_VERSION` moves to 2 for this cut, and why it happens *before* S16 packaging: once S16 has shipped, a
   `.pixlay` in a user's home turns the same cut into a migration decision.

## Ruling (2026-09-22, human): pixels, not paper

Asked where an export's size comes from — a physical canvas times a resolution, or a pixel count — the
human ruled: **paper was never part of this product and the size is controlled in pixels directly.**
Pixels are the only size the product knows, and S12d executes it. This **amends ruling 16**: its clause
"the sheet size stays a document field, reached from the CLI" is exactly what is overruled —
`edit --sheet` and the field it set go with it.

| # | Question | Ruling |
|---|---|---|
| 17 | Where does an export's size come from: a physical canvas × a resolution, or pixels? | **Pixels only.** `CollageDoc` loses its `canvas` field; millimetres, DPI and every conversion between them leave the code, the flags and the files; **one pixel count (the long edge)** sizes every render, and the window's quality row is that number. |

The basis, in the order the cut pays for itself:

1. **A raster's only intrinsic size is pixels.** Millimetres × dpi is a print instruction layered on top
   of pixels — the same file prints at whatever size its reader divides it by — and this product was
   never asked to speak for a printer. Paper entered as scaffolding: S0's performance spike measured an
   A0 render, and S6 made the file carry the resolution it was asked for. Neither made paper part of what
   a document *is*, and ruling 16's `edit --sheet` (2026-09-22, this morning) kept the concept alive one
   step longer than it was ever requested.
2. **It deletes the last cross-field consistency rule.** "The canvas's aspect must equal the template's"
   existed only because two fields each described the same shape; the export grid's shape *is* the
   template's, so the mismatch becomes unrepresentable instead of validated.
3. **It collapses the export surface to one number.** The window's quality row, `render`'s size flag and
   `probe`'s grid all become the same long-edge pixel count: no conversion, no rounding rule to freeze,
   and no resolution in a file that nobody chose.

## Ruling (2026-09-22, human): no utility pane

Asked whether the sidebar still earns its place once every group it holds has a home elsewhere, the
human ruled it does not: the pane goes, and an `Export…` dialog carries the three export questions —
the format, the output quality, and the filename with a path chooser, asked when Export is pressed.

| # | Question | Ruling |
|---|---|---|
| 18 | The utility pane (`AdwOverlaySplitView` + `AdwPreferencesPage`, the Template / Photo / Framing / Export groups) | **Removed, in the UI steps that own its groups.** Each group already has a home: the template combo becomes S14's candidate gallery, the photo buttons are S13's picker plus S14's add/remove and S15's replace/clear, framing is S15's floating buttons plus the gestures, and export becomes the `Export…` dialog below. What has no other home — the frame's gap/radius/colour — moves into a small `Frame…` dialog of the same shape rather than keeping the pane alive for three rows. |

The basis:

1. **A linear three-minute flow has no use for a permanent panel.** The pane was the editor's
   instrument board; the product is now `pick → layout → compose`, and each stage owns its own
   controls (the tray, the gallery, the floating buttons, the dialog). Keeping the pane would mean
   maintaining two surfaces for every one of those decisions.
2. **The export dialog is the standard shape, not an invention.** GTK4's `GtkFileDialog` takes no
   custom widgets, so format + quality + filename-with-path-chooser as rows of an `AdwDialog` is
   the platform's own answer — the same shape the unsaved-changes confirmation already uses.
3. **The frame dialog is the same shape for the same reason.** Three normalized rows behind a
   header-bar `Frame…` button on the compose stage, like `Export…`: one pattern for both
   document-level questions, neither of them a permanent row.

## Ruling (2026-09-22, human): the picker, as gthumb has it

Shown gthumb and loupe at work — both cloned under `~/projects` (`gthumb` at 4.0.rc, `loupe` at 51.0.0,
both read on 2026-09-22) — and asked why the picker does not look like them, the human ruled that the
copy of gthumb's interface is not good enough: the media area takes the vast majority of the page, the
thumbnails fill the full width, the picked list is as tall as the media area, a status bar closes the
window, and clicking a row of the right-hand list switches the preview to that photo. The preview image
being drawn too large is a real defect, not a matter of taste. On the theme, the ruling is that HIG
states the dark theme is the default for video and audio applications. The look that is being copied
is in two screenshots of the reference (3839x2159 device px on a 2× display); every number in this
ruling is measured off them.

| # | Question | Ruling |
|---|---|---|
| 19 | The picker's proportions and arrangement | **The media area takes the vast majority of the page; the thumbnails are one row along its bottom, spanning the full width; the picked list runs down the right edge at the media area's own height; a status bar closes the window.** S13b's arrangement — a small preview above a tall grid, with the picked list down the full page — is superseded. |
| 20 | The bottom of the window | **A status bar with four fields, in gthumb's order: `picked / total`, the photo's pixels, its file size, and the current zoom percentage.** |
| 21 | The picked list | **Clicking a row switches the preview to that photo.** S13b's list only selected (the preview followed the *grid's* click). |
| 22 | "The preview image is too large — you definitely copied it wrong" | **The decode is the size that is drawn, and a cell is gthumb's own size.** `preview_px` follows the photo's *fitted* device size (S13b asked for the pane's long edge whatever the photo's aspect), and **`TILE_SIZE` goes 256 → 128 logical px**: gthumb's `thumbnail-size` default of 256 is *device* pixels, and the reference's own cells measure 250 device = **125 logical** on this 2× display, so S13's ruling read the unit wrong and our cells are twice as big as the app they were copied from. |
| 23 | The theme | **The app is dark by default.** HIG `guidelines/ui-styling`: "apps can alternatively choose to use the dark style by default … **primarily recommended for apps which display rich visual content like images or video**", and both reference apps do exactly that — gthumb `style_manager.color_scheme = Adw.ColorScheme.FORCE_DARK` (`gthumb/src/Application.vala:676`), loupe `// Force dark theme` + `set_color_scheme(adw::ColorScheme::PreferDark)` (`loupe/src/application.rs:76-79`). `AGENTS.md`'s "never force light or dark" is **superseded**; "no per-app style preference" **stands** (neither reference app has one, and a stored preference would need a settings file — ruling 8). |
| 24 | Buttons and menus | **They follow the two references and HIG `patterns/containers/header-bars`**: primary and navigation actions at the **start**, the heading in the **centre**, the menu at the **end**; one **primary menu** with sections, in the shape both apps use ([new / open / import] · [view options] · [keyboard shortcuts, about]). S13b's headers put *every* control at the end and styled the flow's Next button `suggested-action`, which HIG asks header bars to avoid. |

### What the reference actually measures

Both screenshots are the whole screen (3839x2159 device px, a 2× display), the app window starting under the
26-logical-pixel GNOME top bar. Measured off them (`magick`, 2026-09-22; device px, logical = device / 2):

| Band | Reference | Logical |
|---|---|---|
| header bar | y 54..128 | 38 |
| **media area** (the photo's backdrop) | y 132..1851 | **860** |
| **thumbnail row** | y 1852..2080, cells left-aligned from x 41, pitch 250 | **114**, cells **125** |
| **status bar** | y 2094..2157 | **32** |
| media area as a share of the content band (y 132..2080) | 860 / 974 | **88 %** |
| the media backdrop's colour | `#222226` | = libadwaita's dark `--window-bg-color` (measured: `@define-color window_bg_color #222226` in libadwaita 1.10's dark block) |
| the status line itself | `6/6   1254 × 1254   1.1 MB   79%` | count/total · pixels · size · zoom |

And the reference's own code for the pieces being copied:

- **The dark app**: `gthumb/src/Application.vala:676` `style_manager.color_scheme = Adw.ColorScheme.FORCE_DARK;`
  (unconditional, inside `init_settings ()`), the same function that installs the stylesheet
  (`:678-680`); `loupe/src/application.rs:76-79`. HIG `guidelines/ui-styling` is quoted in ruling 23.
- **The media backdrop**: loupe draws it as a constant colour (`src/widgets/image.rs`,
  `BACKGROUND_COLOR_DEFAULT = #222226`) and re-guesses it per image
  (`src/widgets/image/background_color.rs`); gthumb pins a class — `data/css/style.css:5-7`
  `.image-view { background-color: #111; }`, applied at `src/Ext/Image/ImageViewer.vala:17`. **We copy the
  idiom, not the literal**: dark by default and the media area on the theme's own background — which *is*
  `#222226` in the dark scheme, exactly what both references show — because HIG `guidelines/ui-styling:39`
  asks custom styling to use the theme's variables.
- **The thumbnail row**: gthumb's grid is `GtkGridView` with `max_columns=15`, class `thumbnail-grid`
  (`data/ui/file-grid.ui:14-20`), styled `data/css/style.css:26-42`: `.thumbnail-grid { padding: 10px }`,
  `> child { margin: 10px; border-radius: 10px; border: 1px solid var(--dimmed-border-color) }`,
  `.thumbnail-card { padding: 6px; border-radius: 4px }`, and the drop-target edge in the accent. The cell
  size comes from `thumbnail-size` — **default 256** (`data/schemas/org.gnome.gthumb.gschema.xml:31-33`),
  adjustable 128..512 in steps of 32 (`data/ui/browser-preferences.ui:82-89`) — and is consumed as
  `thumbnailer.requested_size` (`src/FileGrid.vala:21-27`), i.e. in the *device* pixels the thumbnailer
  produces. loupe's own thumbnail constant is also 128 (`src/widgets/image.rs: THUMBNAIL_SIZE 128.0`).
- **The zoom readout**: gthumb `zoom_info.label = "%d%%".printf ((int) Math.round (image_view.zoom * 100));`
  (`src/Ext/Image/ImageViewer.vala:665`); loupe formats `"{} %"` from
  `(zoom_target * 10_000.).round() / 100.` (`src/widgets/image_view.rs`) and shows it in the zoom popover.
  **100 % means one image pixel per device pixel in both** (loupe: `applicable_zoom = zoom_normalize(zoom)
  / scaling`).
- **The status line's fields**: the pixel pair is `"%d x %d"` (`gthumb/src/lib/util.c:921`), the size goes
  through `GLib.format_size`, the position is `"%d"` + `" / %u"` (`src/ViewerStatus.vala`), and gthumb's
  browser keeps them in a `GthStatus` inside the bottom bar's right-aligned cluster
  (`data/ui/browser.ui:382-391`, styled `.statusbar { padding: 4px }`).
- **The chrome**: HIG `patterns/containers/header-bars` (primary buttons at the start, heading in the centre,
  menus at the end; group with spacers; tooltips on primary controls; avoid text-only and suggested-action
  buttons in a header bar). gthumb's browser header bar: start = [previous, next, up, reload, selections],
  end = [presentation, properties, edit, comment, Tools, hamburger]; its hamburger is 10 items in 3 sections
  (New Window, Open…, Open Clipboard, Import Files · Sort Files, Sort Folders, Hidden Files · Preferences,
  Keyboard Shortcuts, About). loupe's: 5 sections (New Window, Open… · Open With…, Print… · **Rotate** as
  `display-hint="inline-buttons"` · Set as Background…, Delete · Help, Keyboard Shortcuts, About). Both
  load their menus from per-page `.ui` models; loupe's zoom and prev/next controls are **overlay controls on
  the photo** (bottom-left and bottom-right, faded out after 3 s idle), and its header bar is a `LpShyBin`
  so a long filename cannot grow the window.
- **The shortcuts**: gthumb keeps them as **data** in one table plus a manual key dispatcher
  (`src/Ext/Shortcuts/Shortcuts.vala:132-294`, `MainWindow.vala:1040-1067`, `:1218-1220`) and shows them in
  an `AdwShortcutsDialog`; loupe declares them per action and ships a `shortcuts-dialog.ui`. pixlay already

## S9 · Library and selection on the CLI — ✅ done (2026-09-22)

**Goal**: stages 1–2 of the flow exist as machine surface, so the picker's pixels and its cost can be
measured without a window (`AGENTS.md`: nothing may be possible only in the GUI).

- **Work**:
  - `pixlay-render scan --dir <path>`: the image files of a directory as JSON — path, mime type, size
    *after* EXIF rotation, the EXIF date when there is one, and `mtime`; ordering is lexical by path and
    stable across runs; a file the decoder refuses is a row with its reason, not a silent skip. No
    recursion unless `--recursive`.
  - `pixlay-render thumb --photo <path> --px <n> --out <file>`: one thumbnail's pixels as a file, so the
    picker's expensive half is a CLI number (`AGENTS.md`: a visual conclusion must become a number).
  - `pixlay-render init --template <name> --photo <p>… --out <file>`: extends the existing `init` with
    photos, **argument order = cell order**. This is the "selection becomes a document" mapping that S13
    and S14 both reuse.
  - `pixlay-core` gains the **selection policy** as pure functions (no GTK, no filesystem): the ordered
    photo list, the 2..=9 clamp, the layouts that survive a count (`templates` filtered by
    `template.slots.len()`), and the LIFO add/remove rule against a `CollageDoc`. Putting it in core is
    what lets S13/S14 share one implementation and what keeps its tests display-free.
- **Exit criteria**:
  - `scan`'s JSON field set is fixed and asserted; two runs on the same directory are byte-identical;
    a fixture directory (PNG, JPEG, HEIC, 16-bit PNG, an EXIF-Orientation-6 file, a non-image, an
    unreadable file) produces exactly the expected rows, reasons and exit codes; the reported size of the
    orientation-6 file is the **rotated** one.
  - `init --photo` N times gives N cells whose sources are the arguments in order; N outside 2..=9 is
    refused naming both bounds (`EXIT_USAGE`); a template whose slot count differs from N is refused
    naming both numbers.
  - the LIFO rule is asserted on the document: a remove clears the last occupied cell and nothing else,
    the other cells keep photo, crop and grade; the add restores it in place.
  - `thumb`'s output has the requested long edge and its cost is recorded — **this is the picker's budget
    number** (`VmHWM` and wall clock, per `AGENTS.md`'s measurement rules).
- **Not doing**: no on-disk thumbnail cache, no XDG thumbnail-spec integration, no recursion into other
  mounts, no EXIF writing, no directory watching.
- **Human**: none.

**Decisions this step made** (recorded in `docs/CONTRACT.md` §5's S9 block):

- **`--photo` is repeatable**, and `image` / `thumb` refuse a second one. The alternative — a second flag
  for `init`'s list — would have given the surface two spellings of the same thing.
- **`scan` filters by extension** (`PHOTO_EXTENSIONS`, ten photo formats, case-insensitive) rather than
  attempting every file: reporting every `.txt` and `.pixlay` as a decode failure would make a folder's
  README into an error row. A file whose extension *is* a photo format and which fails to decode is a row
  with its reason, and the command still exits 0. `--help` documents the same list, and a test fails if
  the two drift.
- **`scan` decodes the frame**, not just the loader's early metadata: `ImageDetails`' dimensions are
  glycin's own "often correct, for an early rendering estimate" — not post-rotation — and the whole point
  of the row is the size a tile is laid out against.
- **`scan` reports `mtime` and paths**, which `AGENTS.md` and §5 otherwise forbid in a result. The rule
  exists so output cannot change between runs, and a directory listing's modification times are part of
  its input rather than contamination; two runs over an unchanged directory are still byte-identical.

  re-stat the filesystem to trust the answer.

  be rendered; `Project::sources` already makes a missing photo a loud failure, and a document written on
  purpose should not be the one exception.
- **`Selection::new` does not enforce the floor**: the tray legitimately holds 0 or 1 photo while the user
  is picking, so the ceiling fires on `push` and the floor when a selection becomes a document. Without
  that split, S13's Next button (insensitive below two) would have no way to hold an incomplete selection.
- **No new dependency**, and no `Cargo.lock` change (the `cargo update --workspace` at the start of the

## S11 · Free rotation, and the frame

**Goal**: ruling 11's free rotation, and stage 6's border/radius/colour — the two contract changes of
this plan.

- **Work**:
  - **Free rotation.** `MAX_ROTATION_DEG` (45°), `CLAMP_ZOOM_LIMIT` (1.5) and `CropFit::rotation_limited`
    with its `widest_rotation` machinery are **removed**. The fit keeps its one job: raise the drawn zoom
    to the value that covers the visible cell at **exactly the requested angle**, never reducing the
    angle. `rotationDeg` accepts any finite value and is normalized to `(-180, 180]` at validation, so a
    dial does not accumulate thousands of degrees in a project file. Old projects stay valid (a widened
    range accepts every value the cap allowed), so `DOC_VERSION` does not change.
    Two facts make this safe and they are the step's probes, not assumptions: the required covering zoom
    as a function of the angle is bounded on `[0°, 90°)` for every slot shape (its worst case is on the
    diagonal, and for the widest shipped slot — a ten-column strip with a 4:3 photo, which S3 measured at
    6.0× upright — the free angle takes it to the order of ten, three orders of magnitude below
    `MAX_ZOOM = 1000`), and **the bitmap's size does not follow the zoom** (a slot's bitmap is the slot's
    own pixel extent, so a larger zoom resamples a smaller source region into the same output — it costs
    less, not more, and S0/S7's memory budget is untouched).
  - **The frame.** `CollageDoc.frame: { gapRel, radiusRel, color }` with serde defaults `0`, `0`, white:
    no version bump, and every existing project renders byte-identically. Both lengths are fractions of
    the canvas **height**, like a text layer's `sizeRel`.
  - **The geometry it implies**, stated once so no session has to re-derive it:
    - the *visible* area of a slot is `slot.outline ∩ rounded_rect(slot_bbox inset by gapRel/2, radiusRel)`
    - the fit's reference becomes the **inset bounding rectangle** (a rectangle, so S3's math is
      unchanged): everything visible lies inside it, so covering it covers the cell, and this is exact
      for a concave slot as well;
    - `radiusRel` is clamped to half the smaller side of the inset rectangle, and `gapRel` is refused
      when the inset would leave a cell empty (the error names the slot);
    - the clip path is the intersection above, so a rounded corner shows the backdrop, not a stretched
      photo.
  - **The decoration stage** in `render::draw`: the canvas is filled with `frame.color` (white by default)
    where it used to be hard-coded white in `draw` and in `probe`; the stage sits after slot compositing
    and before the text layers, which is where the frozen evaluation order already puts "canvas
    decoration".
  - **CLI**: `render --gap … --radius … --border-color …`, and an `edit` subcommand
    (`--slot <i> --rotate <deg> --zoom <z> --offset <x> <y> --clear --out <file>`) so slot transforms can
    be set, and therefore checked, without a window.
- **Exit criteria**:
  - **byte-identity**: a document with no `frame` renders byte-identical to the build before this step
    (the probe's pixels, not an eyeball);
  - **the sweep**: for a grid of angles (including ±180° and the diagonals), zooms, offsets, slot shapes
    and photo aspects, the clamped photo covers the entire visible cell to 1e-6 — the S3 sweep kept, with
    the cap gone and the reference rect in place;
  - **the numbers**: the required covering zoom per (slot, photo) aspect as a function of the angle, its
    worst angle, and the A0 memory/time budget re-measured at that worst angle;
  - **the frame is real**: at `radiusRel > 0` the corners' backdrop-coloured pixel count is > 0 and
    monotone in the radius; at `gapRel > 0` the seam is the requested width in pixels (a probe, not a
    look); with a coloured frame those pixels carry exactly that colour;
  - **grading identity** still pixel-identical; **`.pixlay` round-trip** keeps `frame` and the free
    rotation; **no test still asserts the ±45° cap** (they are replaced by the sweep);
  - `edit` is idempotent on the fit (applying it twice equals applying it once) — the property S3
    established must survive the signature change.
- **Not doing**: mirroring/flip in any form (ruling 11 — it is also added to `AGENTS.md`'s "not doing"
  list so nobody re-adds it), quarter turns as a field, per-cell border colour, backgrounds other than a
  flat colour, drop shadows, movable dividers.
- **Human**: none for the code; the frame's *look* is judged at S15.

## S12b · The preview-grade source — ✅ done (2026-09-22)

**Goal**: S12's number, answered. A gesture step resamples *a copy* instead of the original: a decoded photo
is reduced once to a size the preview needs, cached, and every bitmap the preview builds comes from that
reduction. The export, `draw` and the one-pass `resample` are untouched — the preview simply stops asking the
resampler to read 24 MP for a cell that shows 300 px.

- **Work**:
  - `pixlay-imaging` learns a **preview-grade reduction of a `Source`**: a box/mip reduction to a requested
    long edge, deterministic and exact for integer factors, with the photo's aspect kept to the last bit so
    the fit (`CropTransform::fit`) does not move by a rounding. It is the *decoder's* business in the sense
    §4.1 already fixes (all resampling is upstream of the canvas), and it is not `resample`: no filtering
    beyond averaging, no grading, no quantization — it is data reduction, not the picture.
  - `pixlay_imaging::preview` caches it beside the source it came from (the same path + `mtime` identity, the
    same budget) and `Preview::build` resamples the reduction at the resting grid as well as at the gesture
    grid. The reduction is the reason `MAX_SOURCE_BYTES` can hold a whole selection whatever the photos are:
    a 24 MP photo becomes a ~1-2 MP buffer, so the cache holds *more* documents than before, not fewer.
  - The CLI's `gesture` probe reports the size of the source each build resampled (`src_w`/`src_h`), so "the
    big decode left the step" is a number and not an assumption.
- **Exit criteria**:
  - **the number**: a 24 MP document's warm step is **at or under `GESTURE_STEP_BUDGET_MS`** at the editor's
    own grid and at 1600 (measured by `gesture --stats`, both runs recorded in `docs/CONTRACT.md` §8);
  - **the export path is untouched, byte for byte**: the `AGENTS.md` verification render is identical to the
    build before the step (the S12 trick: both builds, same session, `md5sum`);
  - **the drift is a number with a threshold**: the same document rendered at one size by the preview's path
    and by `render --preview-px` differs by a measured RMSE, recorded in §8 beside S7's 0.0077 — and S7's
    `tests/canvas.rs` (canvas vs the CLI, threshold 6) is *kept* green, which is the criterion that says the
    preview is still the export's own renderer rather than a lookalike;
  - **the reduction is a pure function**: the same file reduced twice is byte-identical, the reduction of a
    file that changed is the new file's (the `mtime` rule), and the fit of a given crop moves by less than
    1e-9 between a reduced source and the original;
  - **memory**: peak RSS on a nine-photo 24 MP document does not exceed S12's measurement for the same
    document (the reduction is smaller than what it replaces);
  - `cargo fmt --check` / `clippy -D warnings` / `cargo test`, and the verification render looked at.
- **Not doing**: no GPU renderer, no second renderer, no change to `draw`'s signature, no change to `resample`
  or to the export's quality path, no reduction stored on disk (it is a cache, not a thumbnail file).
- **Human**: the *look* of a preview at rest (S15's walk judges it with everything else) and, if it has to
  move, the drift threshold the fourth criterion records.

**The blur, diagnosed and measured.** Two defects, and they multiply:

1. The pane's decode was the constant `PREVIEW_PX` = 1024 long edge. This machine's display is **3840x2160**
   (`/sys/class/drm/*/modes`, read 2026-09-22), so a maximized window asks the pane for up to **3.7x** that
   decode.
2. The pane can fall back to a **256 px tile** and stay there. `show_focused` paints the tile whenever one is
   in hand, and `Thumbs::seen` refuses a repeated `(index, preview)` request — so a photo that is focused,
   left and focused again shows its tile for as long as that record lives, and a folder change keeps the
   stale record, because the key has no folder in it. S13's own criterion — the pane against
   `pixlay-render thumb --px 1024` — passes, because it measures a *first* focus.

landscape.jpg`, wall clock including the ~25 ms process start):

| long edge | time |
|---|---|
| 1024 | 229 ms |
| 2048 | 593 ms |
| 3840 | 1112 ms |

So the fix is "decode at the pane's own device pixels, capped", and these are the numbers the cap buys: at
`PREVIEW_MAX_PX` = 2048 a maximized window is upscaled at most **1.9x** and one focus costs at most **0.59 s**,
where 3840 would cost 1.11 s per photo in a stage whose question is "is this the photo I meant".

### The GTK findings this step rests on (measured, 2026-09-22)

Three of them are why the code looks the way it does, and each one was found by measuring rather than by
reading:

1. **GTK binds more items than it shows, and never trims.** A fresh model in a 536x396 viewport binds
   **257** items — the same 257 for 300 photos and for 1000, so it is a constant of GTK's item manager,
   not a function of the folder. "Bound" is therefore not "visible", and the requests follow the screen:
   [`Picker::visible`] intersects the cell's allocation with the scroller's. Two traps inside that test:
   a bound cell that has not been allocated answers `compute_bounds` with its CSS border alone (a 6x6
   rect at (-3,-3), which intersects), and a scrolled list inside a `GtkPaned` is allocated its whole
   *content* when `shrink-end-child` is left at its default, which makes GTK count every item as
   visible. Both are commented where they are handled, with the number.
2. **A request's identity has to carry the folder generation.** The first implementation keyed a request
   by `(kind, index, px)` and dropped a reply whose generation was stale; a *stale* queued job then
   revived the *new* request's key, so the new job was skipped as already answered while its own reply
   was rejected as stale. Measured: six tiles stayed "in flight" for the whole three-minute wait on a
   folder of fourteen photos. `crate::thumbs`' `Key` now includes the generation, and the picker clears
   a reply's *own* in-flight entry before judging whether the answer is still wanted.
3. **The cell's waiting state is a static icon, not a spinner.** A mapped `GtkSpinner` animates even when
   it is clipped away, and GTK keeps 257 cells bound: the ones that are never asked for would spin for as
   long as the folder is open. `image-loading-symbolic` says the same thing and costs nothing.

**Decisions this step made** (all recorded in `docs/CONTRACT.md` §9):

- **`shrink-end-child(true)` on both dividers**, with the reason and the number in the code: it is the
  difference between a grid that is 396 px tall and one that is allocated 300 photos' worth of rows.
- **The pane's "current" state is a thing the layer can be held to** (`Picker::preview_current`): before
  S13b the pane could be showing a tile, or another photo's preview, and nothing named that state, so
  nothing could fail on it.
- **A picture is one buffer, not two** (`Rc<Picture>` in both caches: the `glib::Bytes` the texture reads
  and the texture itself), and painting from a cache is a refcount bump rather than a copy of the pixels —
  S13 copied the whole image on every paint, which for a 9.4 MB preview is a copy per frame.
- **The stylesheet is loaded from the binary** (`include_str!("style.css")`) and installed at
  `GtkApplication::startup`, not at build time: the display does not exist until GTK has initialised.
- **`gtk4`'s feature level moves to `v4_12`** (`Cargo.toml`, and the dependency registry in `AGENTS.md`):
  `GtkListBox::remove_all`, `GtkCssProvider::load_from_string` and — the one that is a real requirement —
  `GdkSurface::layout`, GTK4's only "the window was resized" signal. Below 4.12 the build would compile
  and the preview pane would never follow a resize.
- **Ruling 2's "zoom and pan" stays the editor's**: the stage's preview is `Contain`-fitted and static,
  as S13 read it, and the ruling did not change it.

**Human**: none. The ruling above is the human's input, and the stage's *look* — 256 px cells, a drag that
lands where the hand expects, an arrangement that reads — is judged at S15's walk
(`docs/HIG-REVIEW.md` §2, steps 1–3), which is where S13's three questions went too.

### The decisions this step made

- **The strip is a horizontally-reflowing `GtkGridView`**, `min_columns = max_columns = 1`, inside a scroller
  whose vertical policy is `Never`. That is GTK's own shape for a single-row filmstrip: the list base's
  orientation is the axis items flow along, and one item per vertical slice makes the row single at any
  widget height. It also bounds GTK's live cells at `30 × max_columns` = 30 (`gtkgridview.c`), which is why
  a 300-photo folder's requests drop from S13b's 17 to 9.
- **`TILE_SIZE` is the cell's *image*, not its slot.** A cell's allocation is 128 + the 1 px CSS border, its
  decode is 128 × the screen's scale, and the strip's own height is that cell plus the platform's item
  padding — which the app's stylesheet zeroes for this grid alone (`.thumbnail-grid > child { padding: 0 }`,

### The decisions this step made

- **The band is a band on the document's page, and the flow's third stage is a moment rather than a
  place.** S13's editor page gains a third band (`banner · canvas · gallery`), which is what S15's own list
  means by "template → the S14 gallery": one canvas, one decode pipeline, one document. A second
  `AdwNavigationPage` would have had to own a second canvas. `docs/CONTRACT.md` §9's "will sit between
  them" meant the *flow* and is rewritten there.
- **A candidate is drawn from the copy the canvas already holds.** `Preview::build_at_source_edge` names the
  canvas's own preview-grade edge instead of the candidate's, and the measurement above (0 decodes and
  0.083 drift against 7 decodes and 3.42) is why. It is also the answer to the hazard S12b's fidelity
  ladder named: a copy *larger* than the candidate is a downsampling source, which is what the resampler
  wants; a copy *at* the candidate's size is read at 1:1, where the reduction's own sampling is the
  picture.
- **The gallery is one more job on the canvas's decode worker, and the worker coalesces per kind.** The
  band is rebuilt on every committed edit, so a queue that kept only the newest job of *any* kind would drop
  the canvas's bitmaps for a thumbnail nobody asked to look at. Two jobs, two generations, canvas first —
  which is also what puts the preview-grade copies in the cache before the band reads them.
- **The placeholder is a candidate cell with nothing in it.** The candidates arrive from a background build,
  so a shorter placeholder means the canvas is laid out twice on every open — one more grid and one more
  decode of every photo. Measured: the canvas was **105 px** shorter before the band filled, and the
  eight-photo document was decoded **21** times instead of 7. Same widgets, same height, whatever the theme
  and whatever the font size — the alternative, a hard-coded band height, would have been a number the
  theme could invalidate.
- **Two defects came out of measuring that, and both are fixed here.** `EditorWindow::refresh_document`
  asked for a decode *before the canvas was allocated at all*, which `canvas::preferred_grid` answers with a
  **1x1** grid: a decode of every photo into a single pixel plus a preview-grade reduction of each at that
  size. It now returns early when the canvas has no allocation — the first draw asks with a real size — and
  that is 7 of the 14 decodes the open used to cost. (This is the step's own budget, not a later step's
  work: the number S14's criterion measures is this thread's.)
- **The count rule is `selection::layout_for`, and the LIFO token carries the layout.** Same aspect → same
  recipe family → nearest aspect → library order: pure, so the window's `−`/`+`, the CLI's
  `--add-photo`/`--remove-photo` and the gallery cannot disagree about "the layout with that count". The
  token (`Removed`) gained the template because "brings it back" has to be exact (see criterion 3), and a
  layout the user picked *while the cell was out* is kept when it can host the cell — that pick is newer
  than the token.
- **A candidate is a `GtkToggleButton`, and the highlight follows the document.** HIG
  `guidelines/accessibility` and `guidelines/pointer-touch` then cover a candidate for free (focusable,
  named, `Space` activates it — ruling 9's own reasoning, one step early), and no cell can leave the
  document without a layout: the state is written from the document after every edit, so an undo, a project
  opened or a layout changed from elsewhere cannot leave the highlight lying. The accent border is the
  app's own `.layout-cell.picked` (`style.css`), the same idiom as the picker's highlight.
- **The candidate set is `Selection::layouts()`, and one consequence is deliberate.** A document whose cells
  are not all occupied (a per-cell clear, which S15's own controls will make reachable) has a photo count
  below its slot count, so the current layout is **not** one of the candidates and nothing is highlighted;
  clicking a candidate then switches to a layout with the *photo* count, which drops the empty tail — and
  the thumbnail shows that before the click, because the candidate is the real `SetTemplate` result. Ruling
  25 is what makes the strip the library at that count rather than a filtered combo row.
- **The caption is the template's own name** (`mosaic-8-s14`), which is the identifier `edit --template`
  takes and what the CLI reports; whether it reads well for a person is S15's walk's question, recorded in
  `docs/HIG-REVIEW.md` §2.
- **`HIG-REVIEW.md` was re-read and updated for this step** (`patterns/controls/radio-buttons`,
  `patterns/containers/grid-views`, `guidelines/pointer-touch`, `guidelines/adaptive`,
  `guidelines/writing-style`), and its §1 table gained the two new rows: the band is a radio group —
  "one button in the set should be selected at all times" is what the document-driven highlight guarantees —

The step's fifth exit criterion read "only the template-aspect family is listed". Read literally that is a
**second** filter on top of the count — the retired sidebar's combo row filtered exactly that way
(`templates::of_aspect(doc.template.aspect)`, `crates/pixlay/src/sidebar.rs` at `12e1865^:277-282`) — and

| # | Question | Ruling |
|---|---|---|
| 25 | Which layouts does the gallery list? | **Every layout with the photo count, and only those** — `Selection::layouts()`, spanning the library's aspect families. Choosing a candidate of another aspect changes the sheet's shape, and that is the point of the stage ("preview your photos in different grids"). The criterion's aspect-family sentence is replaced by this reading: the gallery *makes the library visible* at that count instead of hiding it behind a combo row filtered to the document's own aspect. |

Basis, in the order it decides the question:

1. **The count filter is already the written policy.** `pixlay_core::selection::Selection::layouts()` is
   "every template with exactly this many slots, in library order", and that module's own doc names the
   layout stage as one of its two consumers (`crates/pixlay-core/src/selection.rs:9-22`, `:134-148`).

2. **Ruling 10 exists for this list.** The library was grown to ≥3 layouts per count, in ≥2 aspect

   judged by says "every candidate is the user's own photos in that layout" (`docs/HIG-REVIEW.md` §2).
3. **Nothing changes shape without a click.** A candidate of another aspect rewrites the document's shape,

with that count, and only those" — and every later sentence in this file that spoke of an aspect filter on

### The decisions this step made

1. **`Frame…` applies as it moves and has no affirmative.** A dialog whose rows have already changed the
   document has nothing to confirm, and a Cancel would have to unwind a stack of live edits — a second
   undo stack, which is the thing ruling 26 refused for `+`. So the rows are the *gesture* path
   (`EditorWindow::set_frame` keeps the command pending and the quiet commit makes it one step) and the
   dialog's one button is *Close*. HIG's action-dialog advice is followed for the dialog that *is* an
   action (`Export…`: Cancel then Export, the verb on the affirmative).
2. **The two lengths are per cent of the collage's height in the dialog**, fractions in the document. A row
   is a number a person types: "4" reads as a share where "0.04" reads as a mystery, and the conversion
   lives in one place (`dialogs.rs`'s `PERCENT`). The group's description carries the unit once instead of
   both rows repeating it.
3. **The rotate control steps 15°, and the wheel keeps 1°.** The angle is free (S11) so a button has to
   pick a step; 15° makes six presses a quarter turn and is still fine enough to straighten a hand-held
   horizon, and the wheel's 1° stays the fine control on the same axis. It is a *step*, not a cap: nothing
   in the document is limited by it.
4. **The strip is one widget, not one per cell.** Nine cells × five buttons would be 45 widgets and 45
   closures doing five edits; the handlers ask the window which cell is selected. The `+`s stay per slot
   because they *are* per-slot controls (each asks for its own cell's photo).
5. **`EmptyCells` became `CellControls`.** The layer now holds two families, and the name says what it is
   rather than what it started as.
6. **Clear is one command** (above): `Command::ClearCell`, so the CLI flag, the strip's button and the
   canvas's `Delete` mean one thing and one press is one undo step.
7. **The frame became a command** (above): `Command::SetFrame`, the one writer for both surfaces.
8. **The window's tooltips stay sentence case.** HIG `patterns/feedback/tooltips` asks for header
   capitalization; every tooltip in this window has been a sentence since S7, and changing some of them now
   would leave the window inconsistent. Recorded in `docs/HIG-REVIEW.md` §1 as a deviation with its landing
   point: the copy pass belongs with S16's translation work, which re-reads every string anyway.

*(Four of the claims below were corrected the same day, after a review of these two commits — the frame

The mechanism behind the `0x0` the review reported is in the window rather than in the test:

**The fix**: `sync_in` places nothing against a placeholder grid or an unallocated canvas (it hides the

### S15b · follow-up (2026-09-24)

A review of the two commits above found six defects, all of them in the harness or in what the harness paid
for — the product fix (the placeholder guard and the re-sync) was left exactly as it landed. This is the
correction; the four claims it corrects are the ones the note at the top of "S15b · landed" lists.

- **The frame counter was the product's, and it cost the shipped app 60 wakeups a second.** The tick
  callback lived in `EditorWindow`'s `constructed`, and a callback that returns `ControlFlow::Continue`
  keeps GTK's frame clock running for as long as it is installed. Measured (private headless mutter, one
  idle window, `/proc`'s own context switches over 20 s): **1218 (60/s) with it, 2 without**. The counter
  is now `support::watch`'s, installed on the windows the tests build (`tests/support/mod.rs`, keyed by
  window because a frame clock belongs to a surface and `mainpath.rs` holds two), and `EditorWindow`
  installs nothing: the app is back to **2 switches and 0 CPU over 20 s idle**.
- **`support::window`'s frame check could not fail.** With the counter installed, a window ticked at
  **180 frames in 3 s with `is_mapped() == false`** — hidden, and still ticking — so `assert_ne!` on it was
  a tautology in the environment the harness runs in, and `docs/CONTRACT.md`'s "a display that does not
  draw frames fails the run rather than passing it" was not true. The check is now the one claim a test
  here can make and can fail: the compositor **mapped** the window (a condition with `FRAME_PROBE`'s 2 s
  budget, then an assert), and a display that never drives the clock costs a wait that times out and says
  what it saw. `tests/support/mod.rs`'s module doc now says which of the two the frame count is.
- **`FRAME_STALL` was unreachable.** Every `pump` call site passes ≤ 500 ms and the branch needed a single
  call over 2 s; the private compositor then removed the scenario it was written for. Deleted, with the
  three comments that cited it as the recovery mechanism.
- **The re-exec is a hard `mutter` requirement, and the failure now says how to leave it.** It names a
  display of your own with `PIXLAY_TEST_CHILD=1` set (the guard is renamed from `PIXLAY_MUTTER_CHILD`,
  because it also means "use the display I have" when a run sets it by hand) instead of compositors the
  harness cannot start itself. `AGENTS.md` and `docs/CONTRACT.md` name `mutter` as the *test environment*
  and not a product dependency, and this file's two `xvfb-run` lines — the carried-over idiom and S16's
  `check()` note, which now has to verify the chroot's own `mutter` — are corrected.
- **The child now gets the parent's libtest arguments**, so `--nocapture`, a filter and `--test-threads`
  reach a GUI binary. Measured before the fix: a probe's `eprintln!` never appeared although its test ran.
- **`support::canvas_size`'s doc claimed "and its bitmaps are in hand"**, which its body never checked;
  corrected, and `tests/hig.rs` now waits through `canvas_bitmaps`, the function that does check it.

### S15c · landed (2026-09-24)

The batch the order puts first after S15b: the review's own condition on S16 is that the data-loss findings
have remediation **and** regression coverage, and the repository's first hard constraint is that a source
image is read-only. Five findings, five changes, each one with the test that holds it.

- **PIX-001 — an output may not be a source image.** One rule in one place,
  `pixlay_imaging::destination::refuse_source_alias`, asked by `render`, by `thumb` and by the GUI export
  **before a byte is decoded**. Two comparisons, because two different things make two paths one file: the
  **normalized spelling** (lexical — `.` dropped, `..` resolved against the component before it, no
  filesystem access, no symlink resolution) and the **file identity** (device and inode, the only answer
  that sees a symbolic link or a hard link; a path that is not there has no identity and cannot be a source,
  because a source is decoded and therefore present). One sentence comes out of it —
  `refusing to write <out>: it is the source image <photo>` — and each surface reports it its own way: the
  CLI as a usage error (exit 1, stdout empty, nothing decoded, nothing written), the window as a toast with
  the `Export…` dialog left open so the name can be fixed. Tests:
  `pixlay-cli/tests/cli.rs::an_output_that_is_one_of_the_projects_photos_is_refused` — all four spellings
  (the literal path, `nested/../photo.png`, a symbolic link, a hard link), the photo byte-identical after
  each one, a positive control that a *different* existing file is still replaced, and an `--out` naming a
  source that is **not there** refused by the spelling rule alone, which is what makes the answer
  independent of the machine — plus `::thumb_refuses_to_write_over_the_photo_it_reads` and
  `crates/pixlay/tests/export.rs` for the window's own verdict and the writer's guard.
- **PIX-011 — an image export is written atomically, and replacing a file is confirmed.** The writer both a
  document and an image go through is now one function, `pixlay_core::atomic::write_atomic`: a temporary
  file in the target's own directory (dotfile, unique per process *and* per call), the caller's own writer
  into it, flush, `sync_all`, `rename` — and on any failure the temporary file is removed and the target is
  untouched, which is what makes "the previous export survives a full disk" true rather than hoped for.
  `pixlay_imaging::encode::write` streams the encoder through it, so `render`, `thumb` and the GUI export
  all replace a file the same way. On the window's side, an export to a path that is already there is
  confirmed first: an `AdwAlertDialog` (Cancel and Replace, Cancel first and the default and the close
  response, Replace marked destructive — HIG `patterns/feedback/dialogs`, "Confirmation Dialogs") presented
  **over** the export dialog, so cancelling leaves the rows to edit. Tests:
  `pixlay-core/tests/project.rs::a_write_that_fails_in_the_middle_leaves_the_previous_file_byte_identical`
  (a body that writes bytes and then fails — the disk-full shape — and a rename that cannot happen because
  a directory sits at the name: the previous file byte-identical, the directory untouched, no `.tmp` left),
  `pixlay-imaging/tests/encode.rs::an_export_replaces_the_file_rather_than_rewriting_it` (a hard link to the
  target keeps the old bytes: the target became a *new* file, which is the visible half of "the write is a
  rename") and `::a_failed_export_leaves_the_previous_file_and_no_litter`, and
  `crates/pixlay/tests/export.rs` for the confirmation itself — refusal toast, dialog stays open, Cancel
  leaves the bytes, Replace runs the worker and the file is a JPEG afterwards. The failure is injected at
  the **writer** rather than through the encoder because the encoder's own failures are IO failures, and no
  portable test can make one arrive in the middle of a stream; the image level pins the two consequences
  instead — the target is a new file, and a rename that cannot happen leaves no litter.
- **PIX-015 — `init`'s no-overwrite guarantee is one operation.** `create_new`, not a check followed by a
  write: two `init`s that race leave exactly one winner rather than both seeing an absent path and one
  truncating the other's project, and a symbolic link at `--out` — dangling or not — is a file that is
  already there rather than a name to write through. A failed write removes the file it created, so the
  command never leaves a truncated project behind. Tests:
  `pixlay-cli/tests/cli.rs::two_concurrent_inits_leave_exactly_one_winner` (two processes started before
  either is waited for; exactly one exit 0, one exit 2 with the documented message, and the winner's file
  loads as a whole project) and `::init_refuses_a_symbolic_link_at_the_output_path`.
- **PIX-016 — a save keeps the file's mode.** `write_atomic` reads the target's permissions and applies
  them to the temporary file **before any content goes in**, so a project that is readable only by its
  owner is never readable by anyone else on the way through; a target that is not there yet keeps the
  process's umask default, which is what a new file gets everywhere else. Test:
  `pixlay-core/tests/project.rs::saving_over_a_private_project_keeps_it_private` (0600 stays 0600, 0644
  stays 0644, and a new file's mode equals a file this test writes with `std::fs::write` — measured against
  the environment's own umask rather than written down).
- **PIX-024 — a JPEG past its own size fields is refused.** The format records width and height in 16-bit
  fields, so a grid wider or taller than 65535 px used to be cast into them and written as a file whose
  header disagreed with its pixels. It is now refused before the temporary file exists
  (`EncodeError::JpegSize`), and the buffer check's expected byte count is computed in 64-bit arithmetic so
  the message is the number the check compared against even for the largest grids. Test:
  `pixlay-imaging/tests/encode.rs::a_jpeg_past_its_own_size_fields_is_refused_before_anything_is_written`
  (65535 fits and the `SOF0` records it; 65536, 70000 and a 65536-tall grid are refused with nothing
  created).

  needs the file to exist and resolves symlinks, so it would answer a different question.

- **The alias rule is asked twice on the GUI path** — once by the form (`EditorWindow::export_destination`,

The batch the order puts second — "make large work fail safely" — and it turned out to be two defects

- **PIX-003 — the 200 MP budget, at the boundaries a size is actually asked for.** `PixelSize::validate` is

  long edge, and the grid it scales the base canvas to is what gets allocated, so a square template at the

  naming the slot, the texels and the conversion's peak bytes: `slot 0: bitmap needs 212722225 pixels
  (3890140370 bytes at the conversion peak); the limit is 200000000 pixels`. All three refusals are exit 2
  — the typed `CanvasTooLarge` / `BitmapTooLarge`, not a usage error, because the flag is inside its own
  range and it is the grid or the bitmap that is not — and all three happen before the first decode:
  measured 0.17 s, 0.16 s and 0.20 s, with nothing written.
- **PIX-027A — the aspect is checked before it is used.** `PixelSize::for_long_edge` multiplied by `aspect`
  before looking at it, so `NaN`, zero, a negative and an infinity reached the rounding and came back as a
  one-pixel-by-N grid unrelated to the template. It now requires a positive finite aspect inside the
  template's own domain — the new `MIN_TEMPLATE_ASPECT` / `MAX_TEMPLATE_ASPECT` (0.1..=10.0), which
  `Template::validate` shares instead of keeping its own copy of the numbers — and refuses with the same
  `OutOfRange` the template's own validation raises. Test:
  `pixlay-core/tests/contract.rs::grid_aspect_boundaries` (the four non-numbers, one step outside the domain
  on both sides, and the two edges themselves accepted).
- **What the sweep found, and what the bound deliberately does not cover.** Measured 2026-09-24 over the
  shipped library at every whole degree and six photo aspects (`docs/CONTRACT.md` §8, "S15e"): the worst
  single slot bitmap at A0 is **212.8 MP** — `strip-2-2x1g` at 45 degrees, a half-canvas slot, whose

  `Σ dst_px` has always been measured rather than checked, and turning it into a rule would be a ruling —
  so it is recorded as a measurement instead.
- **The displayed size needs no bound, and the reason is written where the check is.** `Region::display` can
  legitimately be enormous — a 20000-px-wide source in a 1:20000 aspect is displayed 6e11 px tall — while the

  follows the region, so the region is what is budgeted. `Region::conversion_bytes` is the accounting the

  the one buffer that needs its own argument: `16 * dst_w * min(src_h, 262 * step)` bytes, under 84 MB for
  any source inside the decoder's caps, so it never needs a budget of its own.

### S15f · landed (2026-09-24)

The batch about what a cache may answer with — five findings with one subject: *a cached picture has to be
the document's picture*. Three of them are one rule seen from three sides (an identity that was too weak),
one is a precision rule the hard constraints already stated, and one is a report that named the wrong cell.

- **PIX-004 — the identity of a cached bitmap.** `Preview`'s per-grid set was keyed by the grid alone, and
  a cell was carried over whenever the template, the cell and the file's modification time matched. Two
  things the fit depends on were not in that key. The **frame gap**: the fit reads `Frame::covering`
  (the cell's outline clipped to its inset rectangle), so a gap change moves the region every bitmap holds —
  a set carried over from before it holds another region's pixels *and* another displayed-photo size, which
  `draw` then places with the new fit. And the **source edge**: `build_at_source_edge` looked its set up by
  grid only, so a build asking for a finer edge could be answered with coarse pixels and then store them as
  the new edge's own. Both are in the key now — `Grid.source_edge`, and `frame.gap_rel` in `Grid::reuses` —
  and the test pins what is deliberately *not*: the frame's **radius** is the renderer's clip and is never
  subtracted from the covering polygon, and the **colour** is painted after the slots, so a radius-only or
  colour-only change leaves every bitmap bit for bit identical and must not rebuild one (a slider drag is
  every motion).
- **PIX-027C — `source_px` is the maximum.** The field is the CLI's `src_w`/`src_h`, and it is a claim
  about the work a step did: "this build resampled a copy this big". Each rebuilt cell *assigned* it, so
  with sources of different aspects the last cell processed was reported. It is now the maximum over the
  cells a build rebuilt, compared by area so the pair is one copy's own two edges — a width from one copy
  beside a height from another would be a size no copy ever had.
- **PIX-013 — a reduction is stored at 16 bits.** `PreviewSource::new` handed a reduction back at the
  *file's* depth, so an 8-bit photo was averaged, quantized to 8 bits and only then resampled: a
  quantization between two resampling stages, where the hard constraint puts the only one at the end of the
  pipeline. `reduce` now always writes 16-bit samples (`Source::from_samples` takes the depth, which was
  the file's before), and the price is explicit: a reduced copy is `pixels × 8` bytes rather than `× 4`, so
  the source cache's numbers double. A photo at or below the target is *not* a reduction — those samples
  are the decoder's own, bit for bit, and widening them would buy nothing — and the test keeps that case
  pinned to `Depth::Eight`.
- **PIX-009 — `edit` fits against the frame it writes.** `edit_project` fitted the requested crop against
  the document *before* applying the requested `--gap`/`--radius`/`--border-color`, and the fit reads
  `Frame::covering` — so `--slot 0 --zoom 0.8 --gap 0.06` wrote a crop fitted for a frame the file does not
  carry, `draw` refitted it, and the same edit run twice moved the bytes (the second run fitted against the
  frame the first had written). The frame block now comes **before** the framing block, and the new test
  asserts both halves: the stored crop equals `fit_crop`'s answer for the frame in the same file, and two
  runs are byte-identical. Without the fix the test fails on the bytes.
- **PIX-012 — a file replaced in place is a different photo.** The picker's tile and preview caches are
  keyed by `(position, size)`, and a position is not an identity: a photo edited or replaced under the same
  name keeps its index, its cell and usually its size class. `Picker::restamp` is the comparison — the
  modification time **and** the byte count the filesystem reports, one `stat` (~1 µs) taken wherever a
  cached picture would be answered (a cell being bound, a tile being asked for, the pane being refocused) —
  and a file whose stamp moved drops everything cached about that position: its tiles at every size, its
  previews, the photo's own pixel size (the status bar's pixels and zoom are ratios against it), the
  decoder's refusal, and the requests in flight, which are cancelled at the worker so a fresh one goes out.
  A file whose stamp cannot be read counts as changed: a cache may not answer for a file it cannot name.
  What it cannot see is two contents the filesystem describes identically, and that boundary is written
  down rather than papered over.
- **The step's own test found a sixth defect, and it is fixed here too.** The picker's new section (a
  replaced file must reach the tile and the pane) hung for its full 180 s, deterministically: **one tile
  request, nothing built, nothing in flight, no failure, and no cell bound at all**. The cause was in
  `unbind_tile`: GTK unbinds *by position*, and after a folder change the teardown of a stale row arrives
  *after* the same position has been bound again — so the unconditional `cells.remove(position)` threw away
  the **live** cell's entry and, through `drop_tile`, cancelled the tile request that had just been made.
  The cell then sat on its loading state for good: measured, 2831 frames of pumping changed nothing. The
  guard is three lines — only the row that *is* the position's current binding may take its entry away,
  compared as the row's own child against the stored binding — and the test that failed without it passes
  with it. It is not one of the review's findings; it is recorded here because the step's criterion could
  not be met while it existed.

- **A reduction is 16-bit; a photo handed over unchanged is not.** The first is an intermediate between two
  resampling stages and the second is the decoder's own buffer — widening *it* would double the cache's
  bytes to store samples nobody resampled.
- **`source_px` is the maximum over the cells a build rebuilt, as one copy's own pair.** Cells carried over
  from the bitmap cache were not resampled and contribute nothing; the two edges travel together.
- **The picker's identity is the filesystem's, and the boundary is named.** Modification time plus byte
  count, checked by a `stat` where a cached picture would be answered — not a file monitor, not a timer, and
  not a content hash. Two contents the filesystem describes identically are one identity to this cache, and
  the same sentence `pixlay_imaging::Preview` already carries.
- **A stale unbind may not take a live cell's entry.** The guard is the row's own child against the stored
  binding; a position bound twice keeps its *latest* binding, which is the one GTK is painting.

### S15g · landed (2026-09-24)

The batch about geometry consumers — three findings with one subject: *every consumer of a document's
geometry has to answer the question the renderer did*. Two of them are one rule seen from two sides (what a
slot set may be, and what the clamp may do with a region that has no area), and the third is a ruling that
keeps a rule as it stands.

- **PIX-007 — the file's own geometry, checked at load.** The global invariants (pairwise zero overlap, no
  interior hole in the union, cut areas summing to exactly 1.0) were asserted by `tests/templates.rs` over
  the library this build *ships*; a `.pixlay` embeds its own geometry, so a hand-authored file could carry
  two equal overlapping rectangles while `draw` painted cells in index order and `slot_at` answered with the
  first one — the pixels and the hit test disagreeing about who owns a region. `Template::validate`, which
  every load already ran, now checks the slots *against each other*, and the algorithm is
  `pixlay_core::topology`:
  - the canvas is cut into vertical **slabs** at every vertex x *and* every x where one slot's edge crosses
    another's. Inside a slab no vertex and no crossing exists, so the vertical order of the boundary edges
    cannot change: the y-intervals a vertical line sees through each slot keep their shape, their endpoints
    move linearly with x, and **one sample x in the middle is the whole truth about that slab**. No
    sampling *resolution* is involved — a feature that exists somewhere in a slab is measured at whatever it
    measures in the middle of it, which is the one thing a fixed raster cannot promise for an arbitrary
    hand-authored geometry.
  - an **overlap** is a y-span two slots' interval lists share at that x; a **hole** is an uncovered
    interval whose slices cannot reach the canvas border. A gutter is uncovered too and *does* reach it, so
    the two are one question asked at both ends. Connectivity between neighbouring slabs is a **strictly
    positive** overlap of their uncovered slices — the safe direction, because a missed connection would
    report a gutter as a hole while an extra one can only reach the border and hide a pocket.
  - **the sum clause is the coverage identity.** `Slot::area` is already cross-checked against its own
    outline, so a sum above 1.0 can only be geometry that overlaps: refused as `template slots declare 1.2
    of the canvas; at most 1.0 can be covered`, which names the number a caller can compare against the
    canvas. A sum *below* 1.0 is what a gutter layout is, and the complementary half — a template that
    covers the canvas has areas summing to exactly 1.0 — needs no rule of its own, because no overlap plus
    full coverage forces it; `tests/templates.rs` still asserts that equality over the library.
  - `Polygon::validate` gained the outline's own half of the same ruling: **simplicity**, no edge meeting
    another except at the vertex consecutive edges share. A bowtie outline would otherwise give one cell two
    regions (its two halves both answer `contains`); it is refused as `slot 0: outline crosses itself`.
  - **Cost**, measured at the load path's own scale (release, 1000 repetitions). `Template::validate` on the
    8-slot smoke template is **8.5 µs** with the pass and 1.9 µs with it removed; nine slots 8.6 µs, two
    slots 0.7 µs; the whole 26-template library 117 µs. No constant was tuned to make that number look
    good, and nothing else on the load path had to change for it.
  - **Two algorithms, cross-checked.** The library keeps its independent oracle — the 512-sample raster with
    a flood fill from S2 — and `the_loaders_topology_verdict_matches_the_raster_oracle` asserts the two agree
    on every shipped template and on every hand-authored case in that file (refused by both or accepted by
    both). The acceptances are as load-bearing as the refusals: a **gutter** (uncovered, border-reaching) and
    a **slanted cut** off the library's lattice — a shared edge the two slots spell with different
    arithmetic, measured at a **1.1e-16** gap between the spellings at the sample x, which the tolerance has
    to absorb rather than report — both load.
- **PIX-008 — the hit stays geometry-only, and that sentence is now measured.** The ruling of 2026-09-24
  keeps `slot_at`'s answer as the slot's own outline, so this step changed no hit rule; what it added is the
  evidence for both halves in one place,
  `pixlay-render/tests/hit.rs::the_frames_backdrop_pixels_are_still_the_cells_geometry`. `grid-4-2x2` at
  `gapRel` 0.04 / `radiusRel` 0.08 with a backdrop no slot colour is: a pixel in the gap band beside the
  canvas corner and one in a rounded corner (0.15 of the radius along the diagonal from the inset corner,
  outside the disc by 1.2 radii — a clean pixel, not a blend) are both *exactly* the frame's colour and both
  hit slot 0, while a pixel inside the cell is the cell's own colour and hits the cell. The per-slot-colour
  sweep in the same file now runs **with a frame as well as without one**, so "every pixel the renderer
  paints with a slot's colour hits that slot" holds under the frame too. `docs/CONTRACT.md` gained the row
  that says which question `hit` answers — and the boundary the ruling drew with it: a walk that finds a
  person expects the frame's backdrop to select the cell behind it is a **new step after the walk**, not a
  change folded into this one.
- **PIX-027B — a degenerate covering is not a shape to fit.** `CropTransform::fit` documents that a
  degenerate `covering` returns the request untouched; `Frame::new` checked the vertex count and nothing
  else, so a valid three-point *collinear* polygon (or one with a repeated point) reached the covering
  arithmetic and came back fitted — panned, at the request the test uses. The check is now the geometry
  module's own degeneracy (`Polygon::area()` is 0, `NaN` included), and the new rows in
  `pixlay-core/tests/framing.rs` measure the difference instead of describing it: with the check removed,
  the same request against the same collinear region returns `offset (0.406,-0.406)` instead of `(0.5,-0.5)`.
- **What the step deliberately did not do.** No library fingerprint (the ruling keeps the file's own
  geometry usable and checked, not replaced by a table of names), no second hit rule, and no relaxation of
  the frame's clamp reference: the radius is still not subtracted from `Frame::covering`, because the visible
  region is a rounded rectangle whose exact support needs arcs while the reference stays a polygon.

nothing is corrupted*. Two of them carried rulings from 2026-09-24 (PIX-010, PIX-017) and were built to

- **PIX-010 — the export's defaults, its name, and Return.** The ruling's shape: **no chooser step on the
  main path**. The first export of a window lands in the **pictures directory** (`picker::default_folder()`,
  the folder the picker opens on; an account with neither `XDG_PICTURES_DIR` nor `~/Pictures` keeps the bare
  name), and a later one in the directory the last export used, because the stored form keeps the whole path
  and the dialog is seeded from it. The name's extension belongs to the format row: a name carrying the
  other format's extension is rewritten **case-insensitively** and for both JPEG spellings — `Format::from_path`
  is the one rule, so `.jpeg` and `.JPG` are the JPEG format — while a name that already means the selected
  format keeps the user's spelling; a name with no extension, one whose extension this build does not write
  and an empty name are refused with a toast, the same rule the CLI's `--out` meets. `export::run` asks that
  rule again next to the alias rule, so a direct caller cannot write JPEG bytes under a `.png` name. The
  dialog installs its affirmative as libadwaita's `default-widget` — that property's own documentation is
  "The default widget. It's activated when the user presses Enter" — and the test activates *that widget*
  rather than the button it happens to be: the first attempt asserted on the very next frame and read the

  visible rather than hidden.
- **PIX-014 — a worker that cannot start, or that is gone, is a report.** The window had three `expect`ed
  spawns and three discarded send failures: a resource-exhausted start took the window down, and a request
  nobody would answer left the canvas's grid, the gallery's build, a tile's in-flight entry or the export's
  progress bar marked pending for ever — a wait with no completion event. `crates/pixlay/src/workers.rs` is
  the new module and the whole of the mechanism: `Kind` (Decode / Thumbs / Export) × `Down` (Start / Gone)
  is the set of sentences a user can be shown, `WorkerPlan` is how a worker's thread starts (`Run` is the
  product's value; `Fail` returns the error a thread limit would; `Vanish` runs the body nowhere, so the
  request channel has no receiver and the first `send` fails — the branch a thread that died takes), and
  `Decoder`, `Thumbs` and `export::spawn` all answer `Result`. Every request answers whether it was
  queued, and the failing request **clears the state it would have marked pending before it reports**:
  `request_decode` leaves `requested` `None`, `request_gallery` clears `gallery_pending`, the picker removes
  its in-flight key *and* the worker's wanted key and shows the reason in the cell that asked
  (`show_failure`), and `start_export` puts `exporting` and the progress bar back. The decoder reports once
  per window (`decode_reported`): a canvas asks on every resize and every edit, and the fortieth toast about
  the same failure is noise. `EditorWindow::with_workers` is the tests' way in — the worker startup moved
  out of `build()` into `start_workers`, so a test can name a plan after the widgets exist and before the
  window is presented — and `EditorWindow::new` is the product's own construction.
- **PIX-017 — the arrow keys choose a cell.** The ruling: "a navigation model with a visible focus". The
  focus **is** the selection — the one cell every other control acts on — so nothing new had to be drawn
  (the canvas has outlined the selected cell since S7); what was missing was the keyboard's way to set it,
  and the name that tells a screen reader where it is. `EditorWindow::focus_step` is the model: geometric
  (`Template::neighbour`, the function `Ctrl+Shift+Arrow` and `edit --swap` already use), no wrapping at the
  sheet's edge, and the first arrow with nothing focused picks the first cell. `sync_canvas_label` writes
  `Collage canvas, cell <n> of <cells>` on every refresh and keeps the string in `canvas_label`, because
  GTK4 has no getter for an accessible property's value and "the name says which cell" is a claim about a
  string. The framing the arrows used to do kept its behaviour under modifiers: `Shift`+arrow pans by 0.02,
  `Ctrl`+arrow by 0.1, `Ctrl+Shift`+arrow still swaps two cells.
- **PIX-018 — `scan` carries byte paths.** A path off the filesystem is bytes, and the report is a machine
  surface: `report::Field::Bytes` plus one escaping rule (`escape_bytes`) makes both shapes lossless. `\` →
  `\\`, newline / CR / TAB → `\n` / `\r` / `\t`, any other byte below 0x20 or the byte 0x7F → `\xNN`
  (lowercase hex), and any byte that is not part of valid UTF-8 → `\xNN` byte by byte; bytes of valid UTF-8
  pass through unchanged, so an ordinary line is byte-identical to what it was and only a value that needed
  escaping changes. `scan`'s `dir` and every `file.<i>.path` are the path's own `as_bytes()`. The *default

  field line either; `--json` carries the same escaped string, JSON-escaped on top of it, because `\xNN` is
  not a JSON escape. stderr stays plain text by decision: it is diagnostics, not the machine surface.
- **PIX-019 — `long_edge` is the edge the file was rendered at.** `render`'s report said the *export base*

  that was not the file's. It is now `max(out_w, out_h)` of the image just written, for both a full and a
  preview render, and `preview_px` stays the request. Measured: `--preview-px 800` reports `long_edge = 800`
  (`out_w = 800`, `out_h = 600`) where it reported the 4000 default; a full render at `--long-edge 9000`
  reports 9000, and a portrait template at 1234 reports the height as its long edge.

  the `CoreError` instead of swallowing it; the `Frame…` dialog shows the message — which names the slot
  the gap emptied — in its **own** `AdwBanner` above the rows (a toast would be behind the modal, covered
  by its dim), and re-seeds the three rows from the document, so a row can never display a number the
  document does not hold. Nothing is left pending and no commit is scheduled. The step found one more thing
  on the way, which is worth its own line: **GTK defers the value notification that a restore causes to
  after the handler that restored it**, so the echo of the seed arrived as a change, applied cleanly (the
  document's own frame *is* valid) and put the banner away again — the row snapped back and the user was

- **PIX-021 — a failing project names its file.** `CoreError::AtPath` wraps a file-backed load's parse or

**Decisions this batch made** (each one a shape later steps read):

- **The escaping rule is one rule for both report shapes**, and stderr is out of it. A machine consumer
  reads `--json` and the line format with the same code; a human reads stderr. Escaping diagnostics would
  buy the machine nothing and cost a reader the path they are trying to copy.
- **`long_edge` reports what was rendered, and `preview_px` reports what was asked for.** The alternative —
  a third field naming the export base — was declined: the base is not a fact about the file, and the field
  a consumer compares two renders with has to be the one they differ in.
- **A worker's failure is one sentence per worker and per way of being down**, in `workers::Kind::message`,
  so the three surfaces cannot word the same state differently; the decoder's own report is additionally
  once per window. The raw reason (the `io::Error`, the closed channel) goes to the log line, not to the
  user.
- **The tests' failure injection is a *plan*, not a mock.** `WorkerPlan::Fail` and `Vanish` produce the two
  states the product's own code paths already handle, so nothing in the shipped path exists only for a
  test: `Run` is what `EditorWindow::new` passes and what every other comment in those modules is about.
- **The arrow keys are the focus; the framing kept its behaviour under modifiers.** The alternative —
  arrows panning and something else (Tab? a mode?) choosing cells — would have left the main path's cell
  choice without a key, which is the finding. HIG's "the main path must be walkable with the keyboard
  alone" is what the change is for, and `tests/keyboard.rs` now walks it without a pointer.
- **A refused row is restored *and* reported**, in the dialog rather than in a toast, because the modal dim
  is exactly where a toast is not read. The restore is what makes "the row shows what the document holds"
  true again, and the echo check is what keeps the report from being undone by its own restore.
- **`AtPath` wraps parse and validation failures only.** An I/O failure already names its file; a second
  path prefix would be a message that says the same thing twice, which is how a real path ends up
  unreadable in a bug report.

## S15j · The picker's preview zooms — ✅ done (2026-09-25)

**Goal**: ruling 2's "a large preview that can zoom and pan" is implemented in the form the 2026-09-24
ruling fixed (PIX-028): **fit ↔ 1:1**, and panning while at 1:1 — the case for it is judging a photo's own
sharpness and telling near-duplicates apart, which is what picking photos needs.

- **Work**: the preview toggles between the `Contain` fit and 1:1 at the pointer (a key and a double click,
  and the same key back to the fit); while at 1:1 it pans by drag, bounded by the image's own edges; the
  decode follows the view — the visible region at the size it draws, which is S13b's rule unchanged, not a
  second one; the status bar's zoom readout follows the view rather than the fit; and the widget's
  accessible name and tooltip say what the toggle does.
- **Exit criteria**: both states are reachable, the toggle has a keyboard path and reverts; a pixel probe
  shows the 1:1 view is decoded at the pane's size rather than upscaled from the fit (the probe samples a
  detail that only survives a real 1:1 decode); panning stops at the image's edges; the window's HIG re-read
  covers the new interaction and `docs/HIG-REVIEW.md` §2's picker item names it; `docs/CONTRACT.md`'s "the
  stage has no zoom of its own" clause is replaced by the ruled behaviour.
- **Not doing**: no free or continuous zoom (ruled), no view rotation (ruled: EXIF orientation is applied at
  decode, and a cell's rotation is the editor's), no fullscreen.
- **Human**: none — the ruling above is the decision; the *look* of the zoomed preview is judged at S15's
  walk, which comes after this step.

**Result**: the two states are built, the toggle is reachable both ways, and the 1:1 view is the photo's own
pixels as a number rather than as an impression. What landed, and the decisions the step had to make on its
own:

- **One new call, not a second pipeline.** `pixlay_imaging::thumbnail_region(source, rect, long_edge)`
  resamples a rectangle of a photo to the size it is drawn at; `thumbnail` is now the whole-photo case of it,
  so there is one resampler, one colour path and one budget check. The 1:1 view passes the rectangle's own
  long edge, at which the Lanczos taps degenerate to the **identity** — measured through the CLI: `thumb
  --px 1600 --region 200,100,800,600` of the 1600x1200 fixture differs from the same crop of `thumb
  --px 1600` in **0 of 480,000 pixels**, and the imaging test holds four rectangles (the whole photo, a
  middle one, one touching the far corner, and a single pixel) to the same standard row by row. A rectangle
  the photo does not contain is refused rather than clamped (`ImagingError::RegionOutside`, with the photo's
  size in the message), because the resampler clamps its *taps* into the source and a rectangle hanging off
  the edge would otherwise smear the last row into a picture of the wrong size.
- **The CLI carries it, because nothing may be possible only in the GUI**: `thumb --region x,y,w,h`, with
  `--px` still the output's long edge, so `--px` equal to the rectangle's own long edge is exactly the
  window's 1:1 view. The refusals split the way the surface's rules do: a malformed rectangle (not four
  numbers, negative, fractional, or with no area) is a **usage** error (exit 1, `--px 0`'s own kind), while a
  well-formed one the photo does not contain is exit **2** and names the file's size — only the decode knows
  that, so it cannot be a usage error. The report gained `region`, the rectangle printed back, so "which
  pixels are these" has one answer whichever spelling the caller used.
- **The pane's own state**: `Zoom::{Fit, Actual}` plus a pan *relative to the centre* (in the photo's own
  pixels), so focusing another photo or resizing the pane keeps the centre and only the photo's own edge
  moves the view; the zoom state itself survives a focus change, because comparing two photos at 1:1 is one
  toggle and then a click. The request identity became `(index, View)` — `View::Fit { px }` or
  `View::Actual(rect)` — which is what the picker's cache and the worker's dedup and cancellation are keyed
  by, so "the same photo at another place" is another picture: a drag asks for the new rectangle per pointer
  event and cancels the views nobody will look at, which is the coalescing (the worker skips a job whose key
  was cancelled while it waited).
- **1:1 needed a box of its own, and that is the one subtlety.** `GtkPicture` centres its content in the box
  it is given but does not shrink that box to the content (`gtk_picture_snapshot`: `x = (width - w) / 2`),
  and `Contain` scales a content smaller than the box **up** to it — so with the box left at the pane's
  size a photo smaller than the pane would be enlarged and 1:1 would be a lie. The picture's *margins* are
  therefore the box (`Picker::place_picture`: half the slack each side), and the photo is drawn at exactly
  its own pixels, centred. At the fit the margins stay zero and `Contain` fills the pane as it always has.
  The other half of the same decision: **the pan is not a translated texture**. A pan changes the rectangle
  the decode is asked for; between two arrivals the pane holds the previous rectangle still rather than
  moving it, because a translated one would have to be drawn outside its box to fill the pane. Whether that
  reads well is a *look* question and belongs to S15's walk, not to a guess here.
- **The anchor, the key and the labels.** A double click toggles *at the pointer*: the photo pixel under it
  is carried through the two placements (`fit_placement` is `GtkPicture`'s own fit, `actual_placement` the
  1:1 box) and the pan is set so it stays there; `Z` (`win.zoom-preview`, in the table, the dialog's
  "Photos" section and `po/`) toggles with the pane's centre, which is the keyboard path HIG
  `guidelines/pointer-touch` asks of a pointer action. The pane's accessible name and tooltip are written
  per state by one function (`Picker::update_zoom_labels`).
- **The HIG re-read, the deviations and the contract.** `docs/HIG-REVIEW.md`'s read line is S15j's, with
  `guidelines/pointer-touch` (the pane's gestures are that chapter's own "Pan: click+drag"; the double click
  is what it advises against and is recorded in §3 as the pointer's convenience beside `Z`; the pan's
  missing keyboard path is the second recorded deviation), `reference/keyboard` (`Z` is in neither the
  standard nor the reserved set; `Ctrl+0` is already the editor's framing reset) and
  `patterns/feedback/tooltips` (the pane's tooltip, read either side of a toggle by
  `tests/hig.rs::check_picker`; GTK 4.24 exposes no getter for an accessible name, which is why the tooltip
  is the half a test can hold). `docs/CONTRACT.md` §9's "the stage has no zoom of its own" became the ruled
  behaviour, and §5's `thumb` rows carry `--region` and its two refusals; ruling 2's row in this file
  already carried the amendment (S15i).
